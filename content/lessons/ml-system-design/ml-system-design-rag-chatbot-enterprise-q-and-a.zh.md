## 为什么重要
“构建一个能回答公司文档问题的聊天机器人”现在是最常见的 LLM 系统设计题。面试官会检查你能否组织好数据摄取、检索、生成、评估和安全，以及你是否知道 RAG 会在哪里失败。

## 概念
**为什么用 RAG**：单靠 LLM 缺少私有和最新的知识，并且会产生幻觉。检索增强生成在查询时取回相关段落，并要求模型**只依据这些段落作答并给出引用**。与微调相比，RAG 能即时更新（重新索引）、遵守访问控制，并提供可追溯的来源。微调适合风格/格式或领域词汇，而不适合会变化的事实。

**离线摄取**：
1. **连接器**（Confluence、Drive、Slack、工单、PDF），支持增量同步和删除。
2. **解析与清洗**：感知版面的 PDF/表格抽取、去除模板内容、必要时做 OCR。解析质量往往决定回答质量。
3. **分块**：按结构（标题、段落）切成约 200-500 token 的块并留少量重叠；每个块都带上标题/章节路径和元数据（来源、日期、ACL、产品）。太小会丢失上下文；太大会稀释嵌入并浪费提示词 token。
4. **嵌入与索引**：对块做嵌入，存入向量数据库（HNSW ANN），并建立 BM25 关键词索引；保留元数据用于过滤。

**在线路径**：
1. **查询改写**（解析对话历史中的指代、展开缩写、可选的多查询/HyDE）和路由（是否需要检索？）。
2. **混合检索**，**ACL/元数据过滤在搜索内部完成**：稠密检索和 BM25 各取前约 50，用 **RRF** $\sum_r 1/(k+\text{rank}_r)$ 融合。
3. 用 cross-encoder **重排**到前 5-10 个；这通常带来最大的质量提升。
4. **提示词组装**：系统规则（“只根据上下文回答，否则说不知道，并给出引用”）、编号的段落、对话、token 预算管理。
5. **生成**（流式），然后做**引用/忠实度检查**和输出护栏。

**评估（分阶段）**：
- *检索*：在带标注的问题集（问题对应标准段落）上看 recall@k、MRR、nDCG。
- *生成*：**忠实度/有据性**（每个论断都有上下文支持）、回答相关性、与标准答案对比的正确性、对无法回答的问题的拒答率；用经人工标签校准的 LLM-as-judge。
- *线上*：点赞/点踩、转人工率、引用点击率、延迟（首 token 时间）、每次查询成本。

**安全与运维**：在检索时强制执行权限（绝不能依赖提示词），把检索到的文本视为不可信输入（**提示注入**），脱敏 PII，记录审计日志，缓存嵌入和高频答案，对索引和提示词做版本管理，并监控文档和问题的漂移。

**典型失败模式**：分块或解析不佳、召回缺失（答案存在却没被检索到）、文档过期、来源冲突、需要多个段落的多跳问题、长上下文“中间丢失”，以及在没有证据时自信地作答。

## 示例讲解
分块：一份 4,000 词的手册，块大小 500 词、重叠 100 词，步长为 400。窗口起点为 0、400、……、3,600（最后一个到达末尾），所以共有 10 个块。

融合：BM25 排序为 $[a,b,c]$，稠密检索排序为 $[c,a,d]$。取 $k=60$：$a=\frac{1}{61}+\frac{1}{62}=0.03252$，$c=\frac{1}{63}+\frac{1}{61}=0.03227$，$b=\frac{1}{62}=0.01613$，$d=\frac{1}{63}=0.01587$。融合后的顺序：$a,c,b,d$。

容量估算：1,000 万个 1,024 维 float32 块需要 $10^7\times1024\times4\approx41$ GB；int8 量化后约 10 GB。6 个各 400 token 的段落加上 500 token 的指令和历史，每次查询的提示词约 2,900 token。

> [!TIP] 面试技巧
> - 按摄取、检索、重排、生成、评估的顺序讲解，并为每一步说出一种失败模式。
> - 把检索评估（recall@k）和生成评估（忠实度）分开，并说明你会先修哪一个。
> - 在检索时强制执行 ACL，并把检索到的内容视为不可信输入。
> - 知道何时不用 RAG：风格/格式调整（微调）、很小的语料（直接放进上下文）、结构化数据（text-to-SQL 或工具）。
