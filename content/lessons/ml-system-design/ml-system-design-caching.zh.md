## 为什么重要
缓存是降低延迟和 GPU 成本最便宜的方式，出现在每个服务设计中：特征查询、embedding、预测，以及现在的 LLM 响应。面试官想听到：缓存什么、命中率的计算和失效策略。

## 概念
**缓存什么**（从最便宜到复用受限最多）：
- 按实体（用户、物品）缓存的**特征 / embedding**：变化缓慢，被大量请求共享。
- 以输入（或其哈希）为键的**模型输出**：用于热门查询、物品或预计算的 top-N 列表。
- **检索结果**（ANN 候选、搜索结果页）、**LLM 提示前缀**（提供商的 prompt caching 会复用共享前缀的 KV cache）以及**语义缓存**（对查询做 embedding，相似度超过阈值就返回已存的答案）。

**分层**：客户端/CDN $\to$ 进程内（本地 LRU，微秒级）$\to$ 分布式（Redis/Memcached，约 1 ms）$\to$ 模型。

**核心数学**：命中率 $h$、命中延迟 $t_h$、未命中延迟 $t_m$：期望延迟 $= h\,t_h + (1-h)\,t_m$，模型负载降为原来的 $(1-h)$。命中率取决于键的偏斜程度（Zipf 流量很适合缓存）和缓存大小。

**策略**：**TTL**（限定陈旧程度）、**LRU/LFU** 淘汰、write-through 或 cache-aside、对缺失键的**负缓存**。

**常见陷阱**：
- **陈旧 / 失效**：在键中加入**模型版本**和特征版本；部署时失效；根据数据变化速度选择 TTL。
- **缓存雪崩/击穿（stampede）**：热点键过期，数千个请求同时打到模型。使用请求合并、带抖动的 TTL 以及提前刷新。
- **个性化会降低命中率**：缓存共享且昂贵的部分（候选、embedding），而不是最终的单用户页面。
- **隐私**：绝不能把一个用户的缓存结果提供给另一个用户；语义缓存需要范围键（租户/用户）和保守的阈值。

## 示例讲解
排序模型耗时 50 ms；Redis 命中耗时 2 ms。命中率 $h = 0.8$ 时，期望延迟 $= 0.8 \times 2 + 0.2 \times 50 = 11.6$ ms（原为 50 ms），模型只承受 20% 的流量：1,000 QPS 变成 200 QPS，GPU 减少约 5 倍。
如果部署更换了模型但键里没有版本，则在 TTL 过期前一直提供旧模型的分数。用 `model_v7` 作键可以让切换干净利落，代价是缓存冷启动（命中率接近 0，所以要预热或逐步放量）。
