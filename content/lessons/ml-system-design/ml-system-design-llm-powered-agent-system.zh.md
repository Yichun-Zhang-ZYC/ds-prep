## 为什么重要
“设计一个解决客服工单/自动化工作流程的智能体”考察你是否理解：智能体就是带着工具循环运行的 LLM，而难点在于可靠性、成本、安全和评估，而不是模型调用本身。

## 概念
**什么是智能体**：一个反复决定下一步动作的 LLM，它调用**工具**（API、SQL、搜索、代码沙箱、浏览器），观察结果并继续，直到完成或触及预算上限。先从最简单可行的方案开始：单个提示词，然后是固定的**工作流**（提示链、路由、并行调用），只有当步骤数不可预测时才使用自由运行的智能体。

**核心组件**：
- **循环/编排器**：ReAct 风格（思考、行动、观察）或先规划后执行；对步数、token、时间和费用设置硬性上限。
- **工具**：窄而文档清晰的函数，带类型化的 JSON schema，尽量幂等，返回模型能据以行动的简洁、结构化的错误（MCP 之类的标准有助于共享工具）。少而清晰的工具胜过几十个功能重叠的工具。
- **记忆**：工作记忆就是上下文窗口（对旧步骤做摘要或截断）；长期记忆是按需检索的事实和历史结果存储（向量库/键值库），需要有写入策略。
- **多智能体**（路由器、专家子智能体、规划者/执行者）：会增加协调成本和失败模式；只有当独立的上下文或技能明显有帮助时才使用。
- **护栏**：每个工具使用最小权限凭证、沙箱化的代码执行、**对不可逆或高风险动作（退款、删除、发邮件）要求人工审批**、输入/输出过滤，以及**提示注入防御**（来自工具和网页的内容是不可信的数据，绝不是指令；读取权限与执行权限分离）。

**可靠性计算**：错误会累积。若每步成功概率为 $p$，则 $n$ 步任务成功的概率为 $p^n$。对策：减少步数、每步后验证、带反馈的重试、确定性的工作用确定性代码、检查点/可恢复。

**成本与延迟**：每一步都要重新发送不断增长的历史，所以输入 token 大致随步数**呈二次增长**：设系统+工具提示为 $S$，每步新增 $u$ 个 token，则 $\text{总输入}=n\,S+u\,\frac{n(n-1)}{2}$。缓解办法：对稳定前缀使用**提示缓存**、压缩历史、简单步骤用更小的模型、并行工具调用。延迟 = 步数乘以（LLM 耗时 + 工具耗时）；要向用户流式展示进度。

**评估**：构建带自动成功判定的任务集（沙箱环境的最终状态、标准答案，或 LLM/人工评分标准）。跟踪**任务成功率、步数、成本、延迟、转人工率**，并检查**轨迹**（选错工具、循环、幻觉出的参数）。把它作为回归测试集，在每次提示词/模型/工具变更时于 CI 中运行，然后在线上先影子模式再分阶段放量。记录完整的追踪（工具调用、token、延迟），用于调试以及构建微调/评估数据。

**失败模式**：无限循环和重复调用、选错工具、参数格式错误、上下文膨胀、过度信任工具输出、副作用被执行两次、静默的部分完成、成本级联上升。始终提供平滑交接给人工的途径。

## 示例讲解
客服工单智能体：系统 + 工具定义 $S=2{,}000$ token，每步追加 $u=1{,}500$ token（推理加工具结果），共 8 步。

总输入 token $=8\times2{,}000+1{,}500\times\frac{8\times7}{2}=16{,}000+42{,}000=58{,}000$。按每百万输入 token \$3 计算，缓存之前每张工单为 $58{,}000\times3/10^6=\$0.174$；缓存 2,000 token 的前缀能让固定部分大多变得便宜，但不断增长的历史才是更大的一项。

可靠性：若每步正确率为 95%，8 步运行的成功率为 $0.95^8\approx66\%$。把单步可靠性提高到 99% 则得到 $0.99^8\approx92\%$，这就是验证和减少步数很重要的原因。每步 2.5 秒，延迟约 20 秒，因此要流式推送状态更新。

> [!TIP] 面试技巧
> - 说明你会从简单的工作流开始，只在需要时增加自主性，并指出每增加一步的代价。
> - 量化可靠性（p 的 n 次方）和 token 增长，以论证更短的链条、验证和缓存。
> - 把安全放在代码和权限里（最小权限、不可逆动作需审批），并提到提示注入。
> - 把评估描述成可重放的任务集加轨迹检查，而不是只凭最终答案的感觉。
