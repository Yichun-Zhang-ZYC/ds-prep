## Why it matters
Enterprise search (find the right doc across Drive, wiki, tickets, email) is a retrieval problem with hard extras: per-user permissions, many heterogeneous sources, little click data and tight infrastructure budgets. It is the non-generative half of the RAG question, so interviewers use it to see whether you can reason about retrieval quality, security and scale without leaning on an LLM.

## Concept
**Scope**: input = a short query ("Q3 security review", "error E1042"), output = a ranked list of documents with snippets, not a generated answer. For generation on top, see *RAG chatbot for enterprise Q&A*; for the general funnel and LTR, see *Search ranking*. This lesson goes deeper on what is different inside a company.

**What is different**:
- **Permissions**: users must never see documents they cannot open, and ACLs change daily.
- **Heterogeneity**: slides, PDFs, wiki pages, chat threads, tickets; each needs its own parser and its own signals (author, recency, views).
- **Sparse feedback**: few users and few clicks per query, so do not depend on click-trained rankers alone.
- **Mixed intent**: navigational ("benefits page"), lookup of exact tokens (error codes, ticket IDs) and exploratory semantic queries.

**Architecture**:
1. *Ingestion*: connectors with incremental sync and tombstones, parsing (layout-aware), dedup of near-identical copies, chunking by structure with title/path prepended to each chunk. Store **document-level and chunk-level** records; rank documents by aggregating chunk scores (max, or max plus a small bonus for multiple hits).
2. *Indexing*: BM25 inverted index and a dense index (embedding model + HNSW or IVF-PQ), both carrying ACL and metadata fields.
3. *Query path*: query understanding (acronym expansion from a company glossary, spell correction, intent), **hybrid retrieval** (BM25 catches exact IDs and rare terms; dense catches paraphrase) fused with RRF, then a cross-encoder or LTR reranker over the top ~50-100 using text relevance plus recency, popularity, author/team affinity and source type.
4. *Snippets and UI*: highlight the best matching chunk, show source and date.

**Access control**: the standard design is a **permission filter inside the index** (a bitmap or a list of allowed principals per chunk, matched against the user's groups at query time). Post-filtering the top-$K$ results is simple but can return too few results when most hits are forbidden, forcing large over-fetch; pre-filtering with ANN can hurt recall and speed, so use filter-aware HNSW traversal or partition the index by tenant/department. Propagate ACL changes quickly (event-driven re-index of ACL fields only), and fail closed on sync errors.

**Embedding model**: start with a strong general model, then adapt with domain pairs: synthetic queries generated by an LLM for each chunk, hard negatives from near-miss chunks, and later click or reformulation data. Matryoshka embeddings and int8/binary quantization cut memory with a small recall loss; **rescore** the shortlist with full-precision vectors.

**Evaluation**: you rarely have labels, so bootstrap: LLM-generated question-to-chunk pairs plus a few hundred human-judged real queries; measure recall@K (retrieval) and NDCG@10 (ranking), sliced by source and query type. Online: click-through, success rate (a click with dwell or no reformulation), zero-result rate, time to first click, latency. Check permission correctness with adversarial tests (a user must never retrieve a forbidden doc).

**Ops**: freshness SLO (new docs searchable in minutes), index versioning with blue/green rebuilds when the embedding model changes (a full re-embed), per-tenant isolation for SaaS, audit logging, PII handling.

## Worked example
Capacity estimate (illustrative). 20M documents, 8 chunks each, so 160M vectors. Embeddings are 1024-d.

- float32: $1024\times4=4096$ bytes per vector, so $160\text{M}\times4096\approx655$ GB.
- int8 quantized: $1024$ bytes, so about $164$ GB.
- HNSW graph links at roughly 128 bytes per vector add about $20$ GB.

So int8 plus graph is about $184$ GB in RAM, with full-precision vectors on SSD for rescoring. With 64 GB nodes and 50% headroom for the OS, queries and growth (32 GB usable), that is $\lceil184/32\rceil=6$ shards, each queried in parallel with the results merged.

Permission filtering: if a user can see only 20% of the corpus and you post-filter, fetching $K=10$ results needs about $10/0.2=50$ candidates on average, and 75 with a 1.5x safety margin for variance. If the ACL is much more restrictive (1%), post-filtering breaks down, so push the filter into the index.

> [!TIP] Interview tips
> - Lead with permissions: it is the biggest difference from web search and signals real-world experience.
> - Explain why hybrid retrieval beats either alone and where the reranker sits.
> - Do the back-of-envelope: vectors x dimension x bytes, then quantization and sharding.
> - Address the cold start of labels: synthetic queries, a small human gold set, then clicks with bias correction.
