## 为什么重要
许多模型根本不需要在线 endpoint：每晚的流失评分、每周的线索排序、每月的风险分层。面试官会问批处理何时优于在线服务，以及如何让批处理作业可靠且便宜。

## 概念
**批量（离线）打分**按计划在一个大表上运行模型，并把预测写入表或文件存储，由应用和仪表盘读取。

**批处理 vs 在线**：

| | 批处理 | 在线 |
|---|---|---|
| 延迟 | 分钟到小时 | 毫秒 |
| 新鲜度 | 滞后一个周期 | 每次请求 |
| 成本 | 便宜、高吞吐、可用 spot 实例 | 常驻、资源冗余 |
| 特征 | 任何数据仓库数据 | 需要低延迟 feature store |
| 适用 | 推荐列表、流失、信用额度 | 欺诈检查、搜索排序、聊天 |

当实体集合已知、决策不紧迫，或预测可以预先计算（有时还可作为查找表缓存到线上）时，使用批处理。**混合**方案很常见：批量特征和候选分数，加上一个轻量的在线重排器。

**实现模式**：
- **Spark** 或 **Dask**：读取分区表，用 pandas UDF / `mapInPandas` 应用模型（**每个分区加载一次**模型，而不是每行一次），写出分区输出。
- **数据仓库原生**：BigQuery ML、Snowflake 模型函数或 SQL UDF，避免数据搬移。
- 云服务：SageMaker Batch Transform、Vertex AI batch prediction。
- 按 **N 行一块**处理，使推理向量化并限制内存。

**可靠性**：
- **幂等写入**：输出以运行日期为键，用分区覆盖写入，因此重跑和回填不会产生重复行。
- **原子发布**：先写入暂存路径，校验（行数、空值率、与上次相比的分数分布），然后切换或提交。
- 每条预测都记录 `model_version`、`scored_at` 和特征快照日期。
- 显式处理新实体和缺失特征（兜底分数）。
- 监控作业时长、输入输出量和预测漂移；用 Airflow 等工具编排。

**陷阱**：用*今天的*特征为过去某个时刻定义的标签打分（泄漏），或使用预测被使用时还拿不到的特征。

## 示例讲解
一个流失模型每晚为 2000 万用户打分。向量化后每行推理耗时 0.05 ms，所以 $20{,}000{,}000 \times 0.05\text{ ms} = 1000$ s 的计算量。分摊到 50 个 Spark 分区，每个分区约 20 s 的模型时间加上 I/O；在小型集群上几分钟即可完成。

同样的量如果走在线服务，需要一个常驻服务；批处理还允许你做校验：如果今天的平均分是 0.31 而昨天是 0.12，发布步骤会阻止并告警，而不是把错误的分数送进 CRM。对 `ds=2024-06-01` 重跑作业只会覆盖那一个分区。

> [!TIP] 面试技巧
> - 按延迟、新鲜度、成本和特征可用性来比较批处理与在线，并提到混合设计。
> - 展示可靠性：幂等的分区覆盖、先暂存后在校验通过后发布、带版本的输出。
> - 陷阱：每行/每个任务都加载模型，或把未来特征泄漏进历史打分运行。
