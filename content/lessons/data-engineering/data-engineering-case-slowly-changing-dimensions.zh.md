## 为什么重要
人人都能定义 Type 1 和 Type 2。面试官接着会问应用层面的追问：如何增量加载、事实表如何关联到正确的版本、迟到的变更怎么办、什么时候 Type 2 是过度设计？本案例讲的是在生产环境中容易出问题的机制。各类型的定义请参见“缓慢变化维度”。

## 概念
Type 2 客户维度的解题思路：
1. **按属性决定**：只对业务需要按历史报告的属性（地区、客群、套餐）保留历史。拼写错误就地修正（Type 1）。混合处理很常见：Type 6 风格。
2. **表结构**：代理键 `customer_sk`、自然键 `customer_id`、被跟踪的列、`valid_from`、`valid_to`（开放 = `NULL` 或 `9999-12-31`）、`is_current`，可选地加一个被跟踪列的行哈希。
3. **加载**：按自然键用**哈希**比较暂存行和当前行；若不同，就关闭当前行（`valid_to = effective_date`）并插入新行。一个 `MERGE`，或同一事务里的两条语句。
4. **事实加载**：按**事件日期**查找代理键：`event_ts >= valid_from AND event_ts < valid_to`。左闭右开区间可避免重叠和空洞。
5. **幂等性**：重跑同一批变更不能产生重复版本（哈希与当前行相同时跳过）。

常见陷阱：
- **迟到的变更**（搬家的消息晚了两周才报告）需要拆分已有区间，并重新关联中间的事实。许多团队对这类情况接受按当前状态归属，或重建受影响的分区。
- **迟到的事实**指向尚未进入维度的客户：插入一个**推断成员**占位行，真实行到达时再更新。
- **同一天多次变更**：源系统可能只显示最后的状态；如果中间状态重要，就通过 CDC 捕获变更。
- 对易变属性（如 last_login）使用 Type 2 会让表爆炸：把它们放在事实表或单独的小维度中。
- BI 用户若按自然键关联却忘了日期过滤，会重复计数；为常见场景提供只含当前行的视图。

## 示例讲解
客户 42 从 2024-01-01 起住在 NYC，2024-03-10 搬到 SF。订单：03-05 为 100，03-15 为 50。

变更后的维度（左闭右开区间）：

| customer_sk | customer_id | region | valid_from | valid_to | is_current |
|---|---|---|---|---|---|
| 1001 | 42 | NYC | 2024-01-01 | 2024-03-10 | false |
| 1002 | 42 | SF | 2024-03-10 | NULL | true |

- 事实加载：03-05 的订单得到 `customer_sk = 1001`，03-15 的订单得到 `1002`。
- 用 Type 2 按地区统计营收：NYC = 100，SF = 50。若用 Type 1（覆盖）：SF = 150，而上个季度的 NYC 营收会悄悄变小。
- 重跑 03-10 的变更批次时，发现当前行的地区已经是 SF（哈希相同），因此不插入任何行。
- 规模核对（示意）：1000 万客户，每年 8% 变更地区或套餐，每年新增约 80 万行，成本很低。若跟踪 `last_login`，每年可能新增多达 1000 万 × 365 行，就不可行了。

> [!TIP] 面试技巧
> - 一定要说明事实如何选对版本：按事件日期查找代理键，并使用左闭右开区间。
> - 点出生产环境的边界情况：迟到的变更、推断成员、同日多次变更、易变属性。
> - 知道什么时候不该用 Type 2：如果没人问历史问题，Type 1 更简单也更便宜。
