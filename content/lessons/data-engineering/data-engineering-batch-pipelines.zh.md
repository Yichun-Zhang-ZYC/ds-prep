## 为什么重要
大多数公司的数据仍然通过定时的批处理任务流转：每晚加载、每小时聚合、每天刷新 ML 特征。面试官会让你设计一条可靠、可观测、可恢复的批处理流水线。

## 概念
批处理流水线按计划处理有界的一块数据（例如“昨天”）。

典型阶段：
1. **抽取 / 接入**：从数据源（数据库快照、CDC 文件、API、事件日志）拉取数据到原始/落地区。
2. **校验**：模式检查、与数据源比对行数、空值/唯一性测试；失败时停止或隔离。
3. **转换**：清洗、去重、连接、聚合（SQL/dbt、Spark）。
4. **加载 / 发布**：原子地写入目标表（先写入暂存表/分区，再切换）。
5. **触发下游**：刷新仪表盘、通知使用方、启动 ML 任务。

设计原则：
- **按逻辑日期处理**（本次运行负责的那个分区），而不是按“现在”，这样重跑和回填才是确定性的。
- **幂等**的任务：重跑某一天会覆盖那一天的分区，而不是追加重复数据。
- 尽可能**增量**处理：只处理新增/变化的数据。
- **依赖与编排**：一个带重试、超时和 SLA 的 DAG（Airflow、Dagster）。
- **可观测性**：日志、每个阶段的行数、数据新鲜度指标、在失败或异常时告警。
- **迟到数据**：重新处理一个滚动窗口（例如最近 3 天），或使用水位线。

批处理 vs 流处理：批处理更简单、更便宜，也更容易回填；只有当业务需要比批处理频率更新鲜的数据时，才选择流处理。

## 示例讲解
`ds = 2024-06-01` 的每日收入流水线：把订单表快照复制到 `raw/orders/ds=2024-06-01`，检查行数是否在最近 7 天平均值的 ±20% 以内，用 `INSERT OVERWRITE PARTITION (ds='2024-06-01')` 构建这个 `ds` 的 `fct_orders`，然后刷新仪表盘。如果任务在凌晨 3 点失败，重跑会得到相同的结果，不会产生重复。

> [!TIP] 面试技巧
> - 按 接入 → 校验 → 转换 → 发布 的顺序讲解，并加上重试、告警和 SLA。
> - 强调逻辑日期分区、幂等覆盖和可回填性。
> - 提到迟到数据，以及阻止坏数据被发布的数据质量关卡。
