## 为什么重要
重新处理历史数据最能暴露流水线的问题：一次重跑让营收翻倍、一次回填压垮数据仓库，或者悄悄改变了仪表盘已经展示过的数字。“幂等与回填”介绍了相关模式；本课是安全运行回填的操作手册，并回答常见的追问。

## 概念
把每个任务设计成**幂等且以逻辑分区（日期）为参数**，然后把回填作为一次受控操作来规划：

1. **范围**：哪些表、哪个日期范围、为什么（bug、新列、新数据源）。只回填**最小**集合，并列出下游使用方。
2. **依赖顺序**：先上游表（拓扑顺序），再下游。用尚未修复的输入重建集市是浪费。
3. **分区独立性**：多数按日表可以**并行**运行各分区。第 N 天依赖第 N-1 天的表（累计余额、SCD2、滚动总计、`depends_on_past`）必须**顺序**运行，这决定了总耗时。
4. **限流**：限制并发（pool、max_active_runs），避免回填饿死生产加载任务或超出源端 API 限额。
5. **隔离并验证**：写入**暂存表/分支**，与当前输出对比（行数、总和、空值率、变化键的差异），然后**交换或发布**。湖仓的分支/时间旅行让回滚很便宜。
6. **沟通**：重述已发布的数字会损害信任；要公告变更、为修正加上版本或时间戳，并刷新依赖的仪表盘和 ML 特征。
7. **避免隐藏的非确定性**：`now()`、可变维度的“最新”快照、未版本化的参考数据和外部 API 调用，会使回填结果与最初那次运行不同。使用按时间点读取（时间旅行、SCD2）或固定的输入。

陷阱：用追加而不是分区覆盖；对旧日期重放副作用（邮件、推送到生产服务）；在上游完成前回填下游；回填中途更改模式；没有成本估算。

## 示例讲解
Bug：最近 90 天的汇率转换有误。链路：`orders_clean`（按日）到 `daily_revenue`（按日）再到 `customer_ltv`（累计：第 N 天 = 第 N-1 天 + 新增营收）。每个分区耗时 4 分钟；pool 允许 6 个并发任务（示意）。

- `orders_clean`：90 个分区 / 6 并行 = 15 轮 × 4 分钟 = **60 分钟**。
- `daily_revenue`：分区相互独立，同样 **60 分钟**（在 `orders_clean` 完成对应日期之后，或全部完成之后开始）。
- `customer_ltv`：依赖前一天，因此是 90 × 4 = **360 分钟**；并行无济于事。更好的修复方式：从检查点重新计算，或把 LTV 改为按日期对 `daily_revenue` 求和，使各分区变得独立。
- 总计约 480 分钟（8 小时），而一次只跑一个分区则需要 1,080 分钟。

执行：把每张表写入 `*_staging`，将 90 天的总和与旧表对比（预期只有有问题的汇率转换不同，例如总变化为 1.8%），然后在一个事务中交换。向财务团队发布重述说明，并刷新仪表盘。

> - 开头先讲这些性质：幂等任务、逻辑日期分区、确定性输入、原子发布。
