## 为什么重要
“你能保证每笔支付都恰好被统计一次吗？”这个问题能区分出两类候选人：一类理解分布式系统中的故障，另一类只会重复营销口号。你应该能解释投递语义，以及真实系统如何实现“实际上的精确一次”。

## 概念
故障（崩溃、超时、重试）迫使你做出选择：
- **至多一次（at-most-once）**：不重试 / 处理之前提交。消息可能**丢失**，但永远不会重复。
- **至少一次（at-least-once）**：重试直到被确认 / 处理之后提交。**不会丢失**，但可能**重复**。这是常见的默认选择。
- **精确一次（exactly-once）**：每条消息只对最终结果产生**一次**影响。在网络上真正的“恰好投递一次”是不可能的；系统通过组合以下手段实现**精确一次的处理（效果）**：
  1. **可重放的数据源**，并跟踪读取位置（Kafka 偏移量）。
  2. **确定性的处理 + 检查点状态**（Flink/Spark 检查点），与数据源偏移量一致地恢复。
  3. **幂等或事务性的写入端**：
     - 幂等写入：按唯一键 / 事件 ID upsert，这样重复处理某条消息不会产生额外影响。
     - 事务：原子地写入输出并提交数据源偏移量（Kafka 事务配合幂等生产者、Flink 两阶段提交写入端、把偏移量记在检查点中的 Delta Lake 提交）。

端到端的保证取决于最薄弱的一环：一个精确一次的 Flink 任务如果写入一个非幂等的 HTTP API（例如“发送邮件”），副作用仍然可能重复。外部调用要使用**幂等键**，并在下游按事件 ID **去重**（在一个时间窗口内）。

## 示例讲解
一个消费者处理一笔支付，把 `+$50` 写入余额表，然后在提交 Kafka 偏移量之前崩溃了。重启后它会重新处理这条消息：如果用的是 `UPDATE balance = balance + 50`，账户就会被入账两次（至少一次）。如果用 `INSERT ... ON CONFLICT (payment_id) DO NOTHING` 写入流水表，再根据流水计算余额，重复的消息就会被忽略：实际上实现了精确一次。

> [!TIP] 面试技巧
> - 定义至多一次、至少一次和精确一次，并把每一种与提交时机联系起来。
> - 说出“精确一次的效果 = 可重放的数据源 + 检查点状态 + 幂等/事务性写入端”。
> - 提醒外部副作用需要幂等键；只有每一跳都支持，才能实现端到端的保证。
