## 为什么重要
几乎所有数据工程的讨论都从区分两类系统开始：**运行**业务的系统和**分析**业务的系统。把两者混在一起（在生产数据库上跑重型分析）是经典的事故故事，面试官希望你能解释它们为什么要设计得不同。

## 概念

| | OLTP（联机事务处理） | OLAP（联机分析处理） |
|---|---|---|
| 目的 | 运行应用：下单、更新资料 | 分析：上季度各地区的收入 |
| 查询 | 大量按键进行的小型读写 | 少量大规模扫描和聚合 |
| 数据 | 当前状态，高度规范化（3NF） | 历史数据，反规范化（星型模型） |
| 存储 | 行式存储，B 树索引 | 列式存储，压缩，分区 |
| 用户 | 应用程序，数千个并发请求 | 分析师、BI 工具、ML 流水线 |
| 延迟目标 | 每个事务毫秒级 | 每个查询秒级到分钟级 |
| 例子 | PostgreSQL、MySQL、DynamoDB | BigQuery、Snowflake、Redshift、ClickHouse、DuckDB |

- OLTP 需要 **ACID 事务**和并发控制；规范化可以避免更新异常。
- OLAP 针对读取吞吐量优化：列式存储只读取需要的列，压缩减少扫描量，反规范化避免昂贵的连接。
- 数据通过 **ETL/ELT** 流水线或 **CDC**（变更数据捕获）从 OLTP 流向 OLAP，通常有一定延迟（几分钟到一天）。
- **HTAP** 系统试图兼顾两者，但大多数公司仍然把它们分开。

## 示例讲解
产品团队想在仪表盘上看“3 年来每个国家每周的平均订单金额”。在生产 PostgreSQL 上跑这个查询会扫描 5 亿行订单，并在高峰期占用资源。正确做法是每晚（或通过 CDC）把订单同步到 BigQuery，在那里对 3 列做列式扫描几秒钟就能完成，而且不会触碰生产环境。

> [!TIP] 面试技巧
> - 从用途、查询形态、模式、存储布局和延迟几个方面对比两者。
> - 说明数据如何从 OLTP 到达 OLAP（批量 ETL/ELT 或 CDC），以及数据新鲜度上的取舍。
> - 绝不要提议在生产数据库上跑重型分析；可以提到只读副本作为权宜之计。
