## 为什么重要
“设计一条采集网站/应用点击事件并支撑分析的流水线”是最常见的数据工程系统设计题。它考察数据接入、流处理与批处理的选择、存储布局、数据质量和成本。

## 概念
任何流水线设计都可以遵循的框架：
1. **澄清需求**：事件量（每秒事件数、峰值）、延迟需求（实时 vs 每日）、使用方（仪表盘、ML、临时查询）、保留期、隐私约束。
2. **估算规模**：每日事件数 × 每个事件的字节数 → 每日 GB 数、峰值吞吐量、每年的存储量。
3. 从数据源到使用方的**高层架构**。
4. **深入细节**：模式、分区、去重、迟到数据、故障处理。
5. **数据质量、监控、成本、隐私。**

点击流的参考架构：
- **采集**：客户端 SDK 批量发送事件（包含 `event_id`、`user_id`/匿名 ID、`session_id`、`event_type`、客户端时间 `event_ts`、属性）到**采集服务/API 网关**，后者按模式校验、添加服务端时间和基于 IP 的地理信息，然后发布到 **Kafka/Kinesis**（按用户或会话 ID 分区）。
- **原始落地**：一个写入端（Kafka Connect / Firehose）把压缩的原始事件写入对象存储 `bronze/clicks/dt=…/hr=…`——这是用于重放的不可变事实来源。
- **流处理**（Flink/Spark Streaming）满足低延迟需求：实时计数器、会话指标、把特征更新写入在线存储；按 `event_id` 去重，使用带水位线的事件时间窗口。
- **批处理**（Spark/dbt，每小时/每天）：解析、去重、会话切分、过滤机器人、身份打通（匿名用户 → 登录用户），写入按 `event_date` 分区的 **Silver** 层 Parquet/Delta，然后生成 **Gold** 层聚合（DAU、漏斗、留存）。
- **服务层**：数据仓库/湖仓用于 BI 和临时 SQL；OLAP 存储（Druid/Pinot/ClickHouse）用于亚秒级仪表盘；特征仓库用于 ML。
- **横切关注点**：schema registry 和数据契约、数据质量检查（数据量、空值率、新鲜度）、编排（Airflow/Dagster）、PII 处理（对 IP 做哈希、同意标志、删除）、消费者延迟监控。

## 示例讲解
估算：5000 万 DAU × 每用户每天 100 个事件 = 每天 50 亿个事件 ≈ 平均每秒 5.8 万个事件，峰值约 3 倍 ≈ 每秒 17.5 万个。每个原始 JSON 事件约 1 KB：每天 5 TB 原始数据；存成压缩的 Parquet 可能约每天 0.7 TB；Silver 层一年约 250 TB。Kafka 容量规划：如果一个分区能处理约 5–10 MB/s，峰值 175 MB/s 至少需要 20–35 个分区；留出余量，选择 64 个。

> [!TIP] 面试技巧
> - 从需求和粗略估算开始；它们是后面每个选择的依据。
> - 画出 数据源 → 采集服务 → Kafka → 原始区 → 流处理 + 批处理 → 服务层，并解释每个部分为什么存在。
> - 深入讲去重、迟到数据、会话切分、分区和重放；最后讲质量、隐私和成本。
