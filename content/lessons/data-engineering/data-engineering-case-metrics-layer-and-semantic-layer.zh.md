## 为什么重要
“为什么不同仪表盘上的营收不一样？”正是催生指标层的症状。这个案例要求你只定义一次指标，一致地提供给 BI、notebook 和 API，并避开经典的聚合陷阱。可以把它看作数据建模与所有使用方之间的契约。

## 概念
**语义（指标）层**是对**实体、维度、度量和指标**的受治理定义，在查询时编译成 SQL。例子：dbt Semantic Layer/MetricFlow、Cube、LookML、AtScale。

解题思路：
1. **盘点与冲突**：收集主要仪表盘对营收、活跃用户、转化率的定义；每个指标统一为一个定义并指定负责人（营收由财务负责）。
2. **建好基础模型**：粒度清晰、整洁的事实表（星型模型）加一致性维度。指标层无法修复糟糕的粒度。
3. **用代码定义**：每个指标 = 度量 + 过滤条件 + 时间维度 + 允许的维度，写在受版本控制的 YAML 里，并配有测试和文档。
4. **编译并提供服务**：指标层生成 SQL、处理关联，并通过 SQL/JDBC、REST/GraphQL、BI 连接器对外提供。对热点查询做缓存或预聚合。
5. **治理**：负责人、通过 pull request 评审、对“黄金”指标做认证、弃用流程、访问控制和血缘。

指标层必须处理的聚合陷阱：
- **不可加指标**：比率（AOV、转化率）和去重计数不能跨分组求和。存储**可加的组成部分**（和、计数），在查询时相除；或者从原始粒度重新计算去重数。
- **半可加**度量（账户余额、库存）：可以跨账户求和，但不能跨时间求和；跨时间用最后值/平均值。
- 把一对多的表关联到事实表时产生**扇出**：表头级别的度量会按子行重复。先在正确粒度上聚合，或使用 `count(distinct)` / 每个键只求和一次。
- **时间处理**：每个指标一个规范的日期和时区、财年日历、按时间点的维度版本。
- **指标漂移**：BI 工具中定义的分叉；让 BI 查询指标层而不是原始表。

自建还是购买：先用 dbt 模型加指标规范起步；当许多工具和团队消费同样的数字时，再引入语义层。

## 示例讲解
两个仪表盘根据每日数据报告每周的平均订单价值（AOV）。

每日数据（示意）：第 1 天有 4 个订单共 200，AOV 为 50。第 2 天有 2 个订单共 200，AOV 为 100。

- 对每日 AOV 取平均：(50 + 100) / 2 = **75**。错误：它忽略了第 1 天订单更多。
- 正确：总营收 / 总订单数 = 400 / 6 = **66.67**。

指标层存储 `revenue = sum(order_total)` 和 `orders = count_distinct(order_id)`，并定义 `aov = revenue / orders`，因此每个粒度（天、周、国家）都是用求和后的组成部分相除。

扇出案例：把 `orders`（表头营收）与 `order_items` 关联。订单 A（营收 100）有 3 个商品；订单 B（营收 50）有 1 个。在关联结果上做 `SUM(orders.revenue)` 得到 100 × 3 + 50 = **350**，而不是 150。指标层要么在关联前先聚合营收，要么把 `revenue` 标记为订单粒度并按 `order_id` 去重。

指标规范示意：

```yaml
metrics:
  - name: aov
    type: ratio
    numerator: revenue
    denominator: orders
    filter: status = 'completed'
    owner: finance
```

> - 先讲问题（数字冲突）和思路：用代码定义一次，编译成 SQL，服务所有工具。
> - 展示你了解这些陷阱：不可加的比率和去重计数、半可加的余额、扇出、时区。
> - 要谈治理（负责人、PR 评审、认证），而不只是技术。
