## 为什么重要

所有 CI/CD 问题归根结底都是同一个形状：每次提交会运行什么、按什么顺序、什么条件才能放行发布。面试官希望你能描述一条快速、可信、可安全部署的流水线，ML 服务也不例外。

## 概念

流水线是由多个阶段组成的**有向无环图（DAG）**；每个阶段包含若干作业，要么通过要么失败，失败会阻止所有下游阶段（**快速失败**）。

**典型阶段**：
- **构建（Build）**：只构建一次，产出不可变、带版本的制品（wheel、以 commit SHA 打标签的 Docker 镜像）。后续阶段使用该制品，绝不为每个环境重新构建。
- **测试（Test）**：先做 lint 和类型检查（几秒），再做单元测试（快、数量多）、集成测试（服务、数据库），最后是较慢的端到端或模型质量检查。便宜的检查放前面。
- **安全扫描**：依赖与镜像漏洞扫描、密钥泄露检测。
- **部署（Deploy）**：推送到 staging，运行冒烟测试，然后把*同一个制品*晋升到生产。

**提速手段**：并行运行相互独立的作业、缓存依赖和 Docker 层、只运行受影响的测试，并把从提交到反馈的时间控制在约 10 分钟以内。总耗时取决于**关键路径**，即最长的依赖链，而不是所有作业之和。

**持续交付与持续部署**：*持续交付*让每个绿色构建都可发布，生产前需手动审批；*持续部署*则自动发布。生产环节的关卡通常是手动审批、带指标检查的自动金丝雀发布，以及一条命令回滚到上一个制品。

```yaml
# .github/workflows/ci.yml (sketch)
jobs:
  lint:    { runs-on: ubuntu-latest, steps: [ ... ] }
  build:   { runs-on: ubuntu-latest, steps: [ ... ] }
  unit:    { needs: build, steps: [ ... ] }
  integration: { needs: build, steps: [ ... ] }
  deploy-staging:
    needs: [lint, unit, integration]
    if: github.ref == 'refs/heads/main'
```

**对于 ML**：在测试与部署之间加入数据校验和模型质量关卡（指标不低于当前冠军模型），并把数据、代码和模型一起做版本管理。

## 示例讲解

各阶段耗时（分钟）：lint 1、build 5、unit 3、integration 8、deploy-staging 2。`unit` 和 `integration` 都依赖 `build`；deploy 依赖 lint、unit 和 integration。顺序执行需要 $1+5+3+8+2 = 19$ 分钟。并行后关键路径是 build → integration → deploy $= 5+8+2 = 15$ 分钟。优化 `unit` 或 `lint` 毫无作用；优化 `integration` 才有效。

> [!TIP] 面试技巧
> - 按顺序描述阶段：先 lint/单元测试（便宜），构建一次，再做集成测试、安全扫描、staging 冒烟测试，最后是有关卡的生产发布。
> - 要提到“以 commit SHA 标记的不可变制品”和“一条命令回滚”；谈速度时提缓存与并行。
> - 对于 ML，要加入数据和模型质量关卡，并区分持续交付（手动审批）与持续部署。
