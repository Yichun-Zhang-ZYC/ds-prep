## 为什么重要

“你会把这个模型或服务跑在哪里？”是设计面试的常见问题。好的回答会比较运维负担、成本形态、扩缩行为和限制，而不是只说出自己偏爱的技术。

## 概念

处于**控制与便利**光谱上的三个点：
- **虚拟机**（EC2、Compute Engine）：你管理操作系统、补丁、扩缩和资源装箱。控制力最大：可运行任意软件、GPU、大内存、长期进程、本地磁盘。
- **容器**（ECS/EKS/AKS/GKE、Fargate、Cloud Run）：你交付一个到处运行结果一致的镜像；由编排器负责调度、重启和扩缩。你管理镜像和（Kubernetes 下的）集群。
- **无服务器函数**（Lambda、Cloud Functions、Azure Functions）：你交付代码；云厂商按事件运行，可缩容到零，并按调用次数和时长计费。

**成本形态**：虚拟机无论忙闲都是固定费用，所以在稳定的高利用率下划算。无服务器的成本约为 $\text{请求数} \times (\text{单次请求费} + \text{GB-秒} \times \text{单价})$，因此适合流量有尖峰或较少的场景，持续高流量时反而吃亏。**盈亏平衡点**是按量计费账单等于虚拟机固定账单的位置。Cloud Run 这类托管容器平台介于两者之间：按量付费，但限制更宽松，也没有函数运行时的约束。

**运维特性**：
- **冷启动**：新的函数或容器实例在服务请求前需要先启动（几十毫秒到数秒；大型 ML 库和模型会让情况更糟）。可用预置并发或最小实例数、更小的镜像、延迟加载来缓解。
- **限制**：Lambda 超时 15 分钟、内存（10 GB）和包大小有限，且没有 GPU；重量级推理需要容器或带 GPU 的虚拟机。
- **状态**：无服务器和容器应保持无状态；状态放在 S3、数据库或缓存中。
- **扩缩**：函数按请求几乎瞬时扩缩（受并发上限限制）；容器按指标（CPU、请求数）在数秒到数分钟内扩缩；虚拟机通过自动扩缩组在数分钟内扩缩。
- **可移植性与锁定**：容器可移植性最好；函数的触发器和运行时则与厂商相关。

**经验法则**：事件驱动的胶水逻辑、webhook 和类似 cron 的任务适合无服务器；稳定的 API 和微服务适合容器；GPU 推理、大内存作业、授权软件和非常稳定的负载适合虚拟机（或 Kubernetes 中的 GPU 节点）。长时间的批量训练用 Spot 虚拟机最便宜。

## 示例讲解

假设某个 Lambda 的价格为每百万次请求 \$0.20、每 GB-秒 \$0.0000166667（x86，标价；忽略免费额度）。函数以 512 MB 运行 200 ms：每次调用 $0.2 \text{ s} \times 0.5 \text{ GB} = 0.1$ GB-s，因此每次调用成本 $= 0.1 \times 0.0000166667 + 0.0000002 \approx \$1.867 \times 10^{-6}$，约每百万次 \$1.87。一台小型虚拟机约 \$0.0416/小时 $\times$ 730 小时 $\approx$ 每月 \$30.37。盈亏平衡点 $= 30.37 / (1.867 \times 10^{-6}) \approx$ 每月 1630 万次调用，约相当于持续每秒 6 个请求。平均每秒 1 个请求的服务（约每月 260 万次，\$4.9）用 Lambda 更便宜；每秒 20 个请求的服务（约每月 5200 万次，\$98）用虚拟机更便宜，前提是一台虚拟机能承载该负载。

> [!TIP] 面试技巧
> - 从四个维度比较：运维负担、成本形态（固定 vs 按量）、扩缩与限制（超时、内存、GPU）以及冷启动。
> - 给出盈亏平衡的逻辑：低流量或有尖峰时无服务器划算，稳定高利用率时虚拟机和容器划算。
> - 对于 ML 推理：小模型、零星流量用无服务器或 Cloud Run；大模型和 GPU 用专用容器或虚拟机。
