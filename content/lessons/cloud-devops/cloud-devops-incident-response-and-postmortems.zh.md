## 为什么重要
每个生产系统都会出故障，数据、机器学习和平台岗位的面试官会问你出事时怎么做：如何分级、沟通、止损，然后复盘学习。清晰的事故流程和无责复盘文化，是资深候选人与只会写代码的人之间的区别。错误预算见 SLA / SLO / SLI 课程；本课讲人和流程方面。

## 概念
**生命周期**：发现 -> 分级并宣布 -> 止损 -> 解决 -> 复盘 -> 跟进行动项。

**角色**（任何非平凡的故障）：**事故指挥官**负责协调和决策（自己不去排查）、**沟通负责人**按固定节奏向相关方通报、**响应者/领域专家**负责调查。使用同一个沟通频道和同一份时间线文档。

**严重级别**按影响而非原因定义：例如 SEV1 = 面向客户的中断或数据丢失，SEV2 = 严重降级，SEV3 = 轻微。级别决定呼叫谁以及沟通频率。

**先止损，后找根因。** 首要目标是止血：回滚最近一次发布、切换功能开关、故障转移、扩容、限流或暂停流水线。在提出各种理论之前先问“什么变了？”（发布、配置、流量、依赖、数据）。

**指标**：**MTTD**（发现时间）、**MTTA**（确认时间）、**MTTR**（恢复时间；需说明从影响开始还是从发现开始计时）。通过 SLO 燃烧率告警发现问题，好过等客户反馈。针对现象（用户影响）告警，每条告警附上 runbook 链接。

**无责复盘**：几天内写完，关注系统而不是个人。内容包括：摘要与影响（用户、时长、受影响的数据、消耗的错误预算）、时间线、根因与促成因素（用“5 个为什么”，不要停在“人为失误”）、做得好与不好的地方（发现、响应、运气成分），以及带有负责人、优先级和截止日期的**行动项**。要跟踪到完成；没有后续落实的复盘只是走形式。

**数据与机器学习事故**：延迟或错误的数据会悄悄污染看板和模型。加入新鲜度、数据量和 schema 检查；规划回填，并说明哪些下游表或模型版本受影响；重新运行前先隔离坏数据。

**常见陷阱**：所有人都在排查而没人沟通；一次改很多东西；不记录时间线；责怪个人；行动项写成“更小心一点”而不是增加防护措施。

## 示例讲解
夜间特征流水线悄悄加载了一张部分为空的表，推荐模型效果下降。示意时间线（自影响开始起的分钟数）：0 坏数据加载；90 分析师发现 CTR 异常；100 宣布 SEV2 事故，指定指挥官；115 团队问“什么变了？”，发现上游 schema 变更；125 止损：把模型回滚到昨天的特征并暂停流水线；190 表完成回填并验证，特征恢复。

发现耗时 90 分钟（靠人工发现；异常告警可将其缩短到几分钟）；宣布后 25 分钟止损；算到止损，总影响约 125 分钟。复盘行动项：(1) 增加行数异常检查并阻止发布（负责人：数据工程，1 周），(2) 对上游 schema 做契约测试（负责人：平台，2 周），(3) 在服务路径上对特征空值率告警（负责人：机器学习，2 周）。注意这些行动项是防护措施，而不是“更仔细地审查变更”。

> [!TIP] 面试技巧
- 口头讲清循环：发现、宣布、止损、沟通、解决、学习。
- 说“先止损，后找根因”，并列出具体手段（回滚、开关、故障转移、暂停流水线）。
- 强调无责文化，以及有负责人和期限的行动项。
- 针对数据/机器学习，提到静默失败、新鲜度/数据量检查和回填沟通。
