---

## 为什么重要
“我们该不该微调？”是最常见的 LLM 系统设计问题。好的回答会把**知识**问题和**行为**问题分开，并按成本和可逆性给各方案排序。

## 概念
经验法则：**RAG 给模型知识；微调改变模型行为；提示是测试两者最便宜的方式。**

- **提示**（指令、few-shot 示例、结构化输出）。几分钟即可迭代，不需要训练数据，适用于任何 API 模型。局限：长提示每次调用都消耗 token 和延迟，模型也未必能可靠遵循细微的风格或格式规则。
- **RAG**：查询时检索文档并放入上下文。最适合**新鲜、私有、庞大或需要引用来源**的知识。更新是即时的（重新索引），可以按用户做访问控制，基于检索内容也能减少幻觉。局限：质量取决于检索；增加延迟和基础设施。
- **微调**（SFT、偏好微调、LoRA）。最适合**风格、语气、严格的输出格式、领域专项技能，以及把大模型的行为蒸馏到小而便宜的模型中**。需要数百到数千条干净样本和评测集。局限：难以可靠地注入新事实、会过时、可能导致遗忘，且改动需要重新训练。

**决策顺序**：
1. 先建评测集；没有它就无法比较各方案。
2. 先试一个强提示。通过就停止。
3. 缺事实？加 RAG。格式、语气或技能不对，或大规模下提示太长/太贵？微调。
4. 它们可以组合：既遵循你的格式、又善用检索上下文的微调模型是常见的生产方案。

**适合微调的信号**：请求量大（单次节省会累积）、延迟严格或需端侧部署、小模型能学会的任务，或提示无法修复的持续性失败。**不适合的信号**：事实经常变化、标注数据少、需要引用来源或按用户权限控制。

## 示例讲解
一个 few-shot 提示每次请求多出 1,500 个 token。按每 100 万输入 token \$3 计算，每次请求成本为 1,500 × 3 / 1,000,000 = \$0.0045。微调一个小模型可去掉这些示例，一次性成本 \$300（假设其他服务成本相同）。

盈亏平衡：300 / 0.0045 ≈ 66,667 次请求。每天 2,000 次请求约需 33 天；每天 100 次则永远不划算。还要加上隐性成本：数据标注、评测，以及需求变化时的重新训练。

  "options": [
    "每周在这些文档上微调",

    "预训练一个新模型"
  ],
  "explanation": "新鲜、私有且需要引用的知识是典型的 RAG 场景。微调不擅长可靠地存储事实，而且会过时。"

```reveal
{
  "prompt": "团队希望模型“了解我们的产品目录”，同时以固定的客服语气回复。你会如何建议？",
  "answer": "把两个需求拆开。产品目录是会变化、可能需要引用的知识：使用 RAG（对目录做结构化检索）。语气是行为：先尝试带少量示例的系统提示；若不稳定，或在你的请求量下 token 开销太大，则用几百到上千条语气正确的回复微调一个较小的模型（训练提示中包含检索到的上下文）。决策前先建一个同时覆盖事实准确性和语气的评测集，并重新核算成本盈亏平衡。"
}
```

> [!TIP] 面试技巧
> - 把问题表述为知识（RAG）与行为（微调），并把提示作为必须超越的基线。
> - 提到先做评测、成本盈亏平衡，以及 RAG 与微调可以组合。
> - 说出失败模式：RAG 的检索遗漏，微调的过时与遗忘。
