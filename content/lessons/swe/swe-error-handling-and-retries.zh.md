## 为什么重要
分布式系统的故障是局部且不可预测的：超时、503、重复消息、写入只完成一半。面试官借此观察你是否为失败而设计，以及你是否知道没有幂等性的重试会让客户被重复扣款。这对 API 客户端、数据流水线、队列消费者和模型服务调用都适用。

## 概念
**错误分类**：**瞬时性**错误（超时、连接重置、429/503、死锁）重试可能成功；**永久性**错误（400、404、校验错误、鉴权错误、bug）永远不会成功。只重试前一种。HTTP 5xx 和 429 可以重试（遵守 `Retry-After`）；大多数 4xx 不可重试。超时是有歧义的：请求可能已经成功。

**代码中的处理**：捕获具体异常，不要用裸 `except`；添加上下文并重新抛出（`raise ... from err`），让堆栈保留原因；绝不悄悄吞掉错误；对非法输入尽快失败；用 `finally`/上下文管理器释放资源；把内部错误映射为清晰的 API 响应，并带关联 ID 记录日志。保持清晰的边界：库只负责抛出，由顶层决定记录、重试还是返回错误。

**重试**：使用**指数退避** $d_i = \min(\text{cap}, b \cdot 2^i)$ 并加上**抖动**（例如“完全抖动”：在 $[0, d_i]$ 内均匀随机休眠），避免成千上万的客户端同步重试（惊群效应）。限制尝试次数和总时间；始终设置每次调用的**超时**。重试会放大负载：如果 3 层各重试 3 次，故障的后端最多会看到 27 倍流量（**重试放大**）。缓解办法：只在一层重试、使用**重试预算**（例如最多额外 10% 请求）以及快速失败。

**熔断器**：连续失败达到一定次数后，在冷却期内停止调用依赖（打开），之后允许一次试探调用（半开）。它既保护依赖，也保持低延迟。配合**降级方案**（缓存值、默认值、功能降级）和**舱壁隔离**（每个依赖独立的资源池）。常用库：`tenacity`、`backoff`、urllib3 `Retry` 以及云 SDK 内置功能。

**幂等性**：重复执行某操作与执行一次效果相同，则该操作是幂等的。读取、`PUT`、`DELETE` 天然幂等；`POST` 扣款则不是。可以通过客户端提供的**幂等键**（连同结果一起存储，使用唯一约束或 `INSERT ... ON CONFLICT DO NOTHING`）、自然键与 upsert，或确定性输出（覆盖某个分区而不是追加）使写入幂等。投递保证：队列通常是**至少一次**，所以消费者必须幂等；“恰好一次的效果” = 至少一次投递 + 幂等处理。

**流水线**：让任务可重新运行（按分区/日期覆盖）、先写入临时位置再原子重命名或切换、对进度做检查点、失败 N 次后把毒消息送入**死信队列**，并对死信队列深度告警。

**常见陷阱**：盲目重试非幂等调用；没有超时；重试永久性错误；没有抖动；在每一层都记录日志并重新抛出（重复噪声）；捕获 `Exception` 然后返回 `None`。

## 示例讲解
示意的支付流程。客户端用 `Idempotency-Key: abc123` 调用 `POST /charges`；服务器完成了扣款但响应丢失（超时）。客户端用同一个键重试。服务器在表中找到 `abc123`，跳过扣款并返回已存储的响应。没有这个键，客户就会被扣两次款。

退避：基数 0.5 秒、因子 2、上限 8 秒，延迟依次为 0.5、1、2、4、8、8……加上完全抖动后，每个客户端在上界内随机休眠，把 1,000 个客户端分散到整个窗口，而不是在 t = 0.5 秒时同时发来 1,000 个请求。如果每个调用在 3 次尝试中都失败，仅这一层就会让依赖看到最多 3 倍的正常负载，所以重试预算和熔断器很重要。

队列消费者：消息处理完后，worker 在确认前崩溃，消息队列会重新投递。把 `message_id` 与副作用放在同一个事务中存储（唯一约束），重复消息就变成空操作。

> [!TIP] 面试技巧
- 先对错误分类：瞬时与永久，并说明超时是有歧义的。
- 给出重试配方：超时、带抖动的指数退避、有限次数、重试预算。
- 把重试与幂等键搭配，并说“至少一次投递加幂等消费者”。
- 提到熔断器、降级方案，以及流水线中的死信队列。
