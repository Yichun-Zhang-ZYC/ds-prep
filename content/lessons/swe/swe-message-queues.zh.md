## 为什么重要
队列把生产者和消费者解耦、吸收流量尖峰并支持重试，几乎出现在每一个系统设计和 ML 流水线中（事件接入、异步推理、训练触发）。面试官会追问投递语义、顺序和幂等性。

## 概念
**消息队列**（或 broker）位于发送消息的**生产者**和稍后处理消息的**消费者**之间。好处：**解耦**（服务可独立部署和故障）、**缓冲**（尖峰在队列中排队，而不是压垮消费者）、**扩展**（增加消费者）、**可靠性**（失败的工作可重试）。

**两种模型**：
- **工作队列/任务队列**（SQS、RabbitMQ、Celery）：每条消息只发给组内的一个消费者，确认（ack）后删除。
- **日志/发布订阅流**（Kafka、Kinesis、Pub/Sub）：消息追加到分区的、保留的日志中。多个消费者组各自按自己的 **offset** 独立读取，并可回放历史。

**确认与投递保证**：
- **At-most-once（至多一次）**：处理前 ack。没有重复，但崩溃会丢消息。
- **At-least-once（至少一次）**：处理后 ack。崩溃导致重新投递，因此会出现重复。这是实际的默认选择。
- **Exactly-once（恰好一次）**：实际上通过至少一次投递加**幂等消费者**（或事务写入）实现。真正端到端的恰好一次很少见。

SQS 风格的队列有**可见性超时（visibility timeout）**：收到的消息会被隐藏 $V$ 秒。如果没有及时 ack（消费者崩溃或太慢），它会再次可见。失败接收 $N$ 次后进入**死信队列（DLQ）**以供排查。

**幂等性**：让重复处理是安全的，例如以消息或事件 id 作为写入键（`INSERT ... ON CONFLICT DO NOTHING`），或记录已处理的 id。

**顺序**：单个队列或分区保持顺序；跨分区则不保证。使用**分区键**（如 `user_id`）让相关事件保持有序。

**背压（backpressure）**：如果生产者快于消费者，队列深度和延迟会增长。监控**消费者滞后（consumer lag）**，扩展消费者，限制生产者速率，并限制队列长度。

```python
# consumer sketch: at-least-once + idempotent handling
def handle(msg, seen, process):
    if msg["id"] in seen:          # duplicate delivery
        return
    process(msg["body"])
    seen.add(msg["id"])            # record, then ack
```

## 示例讲解
图片上传会触发特征提取，每次耗时 2 s，所以一个消费者每秒处理 0.5 条消息。平均负载是 50/s，所以 100 个消费者就能跟上，但 300/s 的峰值需要 600 个。不如让队列吸收尖峰。在 300/s 的 60 s 尖峰期间，积压增加 $(300 - 50)\cdot 60 = 15{,}000$ 条消息。只有 100 个消费者（容量 50/s，等于正常到达速率）时积压永远无法清空，所以扩容到 150 个消费者（75/s）：净消化速率 $75 - 50 = 25$/s，清空需要 $15{,}000/25 = 600$ s。可见性超时 30 s、任务 2 s 时，崩溃的 worker 的消息会在 30 s 内重新出现。

> [!TIP] 面试技巧
> - 说明你设计的保证级别：至少一次加幂等消费者是现实的答案；对“恰好一次”保持怀疑。
> - 提到 DLQ，以及对有毒消息（poison message）使用指数退避重试。
> - 对比队列与日志：队列在 ack 后删除；Kafka 保留数据并允许回放，这对修复 bug 后重新处理非常有用。
