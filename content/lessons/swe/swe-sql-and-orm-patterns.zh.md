## 为什么重要
几乎每个数据或机器学习服务都要访问关系型数据库。面试会考察：能否在不损害性能的前提下使用 ORM（N+1 问题）、编写安全的参数化查询、理解事务和连接池，以及如何在不停机的情况下演进表结构。查询写法见 SQL 课程，针对数据库的测试见集成测试课程。

## 概念
**访问层**：原生驱动（`psycopg`、`sqlite3`）提供完全控制；**查询构建器 / ORM**（SQLAlchemy、Django ORM）把行映射为对象并跟踪变更（提交时刷新的**工作单元**）。ORM 加快增删改查并提高可移植性；对于重度分析、窗口函数或批量加载，应改用手写 SQL（SQLAlchemy Core、`text()`）或使用数据仓库工具。

**会话与事务**：会话封装一个事务。模式：每个请求/作业一个会话，结尾提交一次，出错回滚，在 `finally`（上下文管理器）中关闭。保持事务简短：长事务会持有锁并造成 MVCC 膨胀。了解隔离级别（常见默认是读已提交；可重复读和可串行化能防止更多异常，但代价是需要重试）。

**连接池**：建立连接开销大，而且数据库有连接数上限（Postgres 通常是几百个）。使用应用级连接池（大小约为进程数 x 线程数，不超过数据库上限），当许多服务连接时再加 PgBouncer 这类服务端池化器。设置超时；及时归还连接；不要在线程或 fork 的进程之间共享同一连接。

**安全**：始终使用**绑定参数**（`WHERE id = %s` / `:id`），绝不用字符串拼接。这能防止 SQL 注入，并让数据库复用执行计划。标识符（表名/列名）无法绑定，需要用白名单。

**N+1 问题**：在循环中惰性加载关联会产生 1 次父表查询加 N 次子表查询。修复方式：预加载（`selectinload` 多发一次 `IN (...)` 查询；`joinedload` 用 JOIN，一对多时可能使行数倍增），或用一条查询取出再在 Python 中分组。可通过查询日志、测试中的计数器或 APM 追踪发现它。

**其他模式**：用**批量操作**（`executemany`、多行 INSERT、`COPY`）代替逐行处理；用**upsert**（`INSERT ... ON CONFLICT DO UPDATE`）实现幂等写入；用**键集分页**（`WHERE id > :last ORDER BY id LIMIT n`）代替大 `OFFSET`（后者要扫描并丢弃行）；只选需要的列；为过滤和连接加索引并用 `EXPLAIN` 检查；并发更新时用版本列做乐观锁。

**迁移**（Alembic、Flyway）：有版本、经评审、在 CI/CD 中应用。零停机变更使用**扩展/收缩**：先加可空列，发布同时写两处的代码，分批回填，切换读取，最后删除旧列。避免长时间锁表（Postgres 中用 `CONCURRENTLY` 建索引）。

**常见陷阱**：会话关闭后再惰性加载；把 ORM 对象直接作为 API 响应；巨大的 `IN` 列表；autoflush 带来的意外；外键缺少索引；在同一事务中混用 ORM 会话和原生连接。

## 示例讲解
示意：某接口列出 100 个用户及其订单。惰性加载会执行 1 + 100 = 101 次查询；每次约 2 ms（含网络往返）就约 200 ms。用 `selectinload(User.orders)` 则只需 2 次查询（用户表，再 `WHERE user_id IN (...)`），约 4-6 ms。

分页：`ORDER BY id LIMIT 50 OFFSET 1000000` 每次调用都要越过一百万个索引条目，页码越靠后越慢。`WHERE id > :last_id ORDER BY id LIMIT 50` 直接在主键索引上定位，第 20,000 页和第 1 页成本相同。代价是不能跳转到任意页码。

转账：扣款和入账必须在同一个事务中。用 `UPDATE ... SET balance = balance - 30 WHERE id = 1 AND balance >= 30` 扣款并检查受影响行数；如果之后入账失败（账户不存在），回滚会恢复扣款。

- 对于表结构变更，描述零停机的扩展/收缩迁移。
