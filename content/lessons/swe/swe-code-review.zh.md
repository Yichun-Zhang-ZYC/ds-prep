## 为什么重要
代码评审是团队保持高质量和传播知识的方式。面试官会问你如何评审别人的代码、如何接受反馈，ML 团队尤其担心 notebook 和实验在上线前从未经过评审。

## 概念
**评审的目标**：尽早发现缺陷，保持代码库一致且可维护，分享知识，对齐设计。目的不是证明谁更聪明，风格上的挑剔应该交给自动化工具。

**作者清单（请求评审之前）**：
- 保持 PR **小**（最好少于约 400 行改动）且只聚焦一个改动。大 PR 只会被略读，而不是被评审。
- 写清楚描述：做了什么、为什么、如何测试、风险、截图或指标。关联工单。
- 自己先审阅 diff，在本地运行测试、linter 和类型检查；先让 CI 变绿。
- 不要把重构和行为变更混在一起。

**评审者清单**（大致按重要性排序）：
1. **设计**：是否符合架构，位置和抽象是否正确？
2. **正确性**：逻辑、边界情况（空输入、null、时区）、并发、错误处理。
3. **测试**：是否覆盖新行为和失败路径，代码出错时测试会失败吗？
4. **可读性**：命名、小函数、注释解释为什么而不是做什么。
5. **安全与数据**：输入校验、密钥、SQL 注入、日志中的 PII。
6. **性能与成本**：意外的 O(n^2)、N+1 查询、把整个数据集加载到内存。
7. **运维**：日志、指标、迁移、向后兼容、回滚。

**数据和 ML 的特殊点**：检查**数据泄漏**（在测试集上拟合、使用未来信息）、可复现性（随机种子、固定版本、配置不硬编码）、训练/服务偏差（train/serve skew）、是否在正确的划分和指标上评估、是否误提交了大文件或密钥，以及是否清除了 notebook 输出。

**把枯燥的部分自动化**：格式化工具（black、ruff format）、linter（ruff、flake8）、类型检查器（mypy）、pre-commit 钩子和 CI 测试，让人专注于设计和逻辑。

**给出反馈**：具体、友善，针对代码而非个人。多提问（“如果 `x` 为空会怎样？”）。标明严重程度：`nit:`（可选）、`suggestion:` 以及阻塞问题。解释原因并提供替代方案。剩余评论只是小问题时就批准。

**接受反馈**：假定对方善意，回应每一条评论，用理由或数据反驳，不要放在心上。评审的响应时间很重要：争取在一个工作日内给出首次回应。

## 示例讲解
一个 1,200 行的 PR 添加了特征库客户端，重构了配置加载，并修改了训练循环。评审反馈：拆分成三个 PR（重构、客户端、训练改动），这样每个都可以独立理解和回滚。在客户端 PR 中，评审者发现 `df.fillna(df.mean())` 在 train/test 划分之前对整个数据集计算（泄漏）、一个未固定版本的依赖，以及没有针对空响应的测试。评论：一个阻塞（泄漏）、一个阻塞（错误路径没有测试）、一个关于命名的 `nit:`。修复且 CI 变绿后，PR 被批准并合并。
