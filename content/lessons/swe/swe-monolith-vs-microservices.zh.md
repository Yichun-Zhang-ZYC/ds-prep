## 为什么重要
“你会用微服务吗？”考察的是判断力，而不是流行词。好的回答是结合团队规模、业务规模和运维成熟度的权衡分析，同样的问题也会出现在 ML 平台中（一个服务应用，还是拆成特征、模型和排序服务）。

## 概念
**单体（monolith）**作为一个整体部署：一个代码库、一个进程（或相同的副本）、通常一个数据库。**微服务（microservices）**把系统拆成小型的、可独立部署的服务，每个服务拥有自己的数据，通过网络（HTTP/gRPC 或事件）通信。

**单体的优点**：开发、测试、调试和部署简单；进程内调用快速且支持事务（模块间 ACID）；运维开销低。**缺点**：扩展只能整体进行，一次糟糕的发布或内存泄漏会影响所有部分，代码库可能变得纠缠不清，构建和发布时间随团队规模增长，且只能用一种技术栈。

**微服务的优点**：每个服务可独立部署和扩展（扩展 GPU 推理服务，而不是管理后台界面）、团队自治、故障隔离、技术栈自由（Python 模型服务与 Go 网关并存）。**缺点**：
- **分布式系统成本**：网络延迟、部分失败、超时、重试以及级联故障。
- **数据一致性**：没有跨服务的 ACID 事务；要使用 saga 和最终一致性，而“每个服务一个数据库”使 join 变得困难。
- **运维开销**：服务发现、可观测性（追踪、指标、日志）、每个服务的 CI/CD、带版本的契约、值班。
- 端到端**测试**更困难。

可用性会连乘：$n$ 个同步依赖，每个为 $a$，则整体为 $a^n$。10 个 99.9% 的服务链是 $0.999^{10} \approx 99.0\%$。

**中间路线**：具有严格模块边界、单一部署单元的**模块化单体**。只有在有理由时才拆出服务：不同的扩展特征（GPU 模型服务）、不同的发布节奏、团队边界，或隔离有风险的组件。常见规则：从单体开始，在痛点出现时再提取服务（**绞杀者模式 strangler fig** 可渐进迁移）。

**通信**：同步（REST/gRPC）简单但会耦合可用性；异步事件（队列/Kafka）解耦但增加复杂度。边缘使用 **API 网关**，服务之间使用超时、带退避的重试和熔断器。

**反模式**：**分布式单体**（必须一起部署或共享数据库的服务），以及过细的“纳米服务”。

```python
# in-process call (monolith): microseconds, shares a transaction
price = pricing.quote(order)
# microservice call: network, can fail or time out
price = http.post("http://pricing/quote", json=order, timeout=0.2)
```

## 示例讲解
一家初创公司有 6 名工程师，应用包含 Web 界面、订单模块和推荐模型。选择：在共享 Postgres 上的模块化单体。成本：一条流水线，结账时事务简单。两年后，推荐器需要 GPU 和 10 倍的规模，40 人的组织也受困于发布冲突。把推荐器提取为服务（`GET /recs` 使用同步 gRPC，超时 100 ms，并回退到热门商品），订单保留在单体中。每一跳增加约 1-5 ms，且由于有回退，推荐器故障不再阻塞结账。
