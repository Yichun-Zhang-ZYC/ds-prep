## Why it matters
Undocumented code and models become tribal knowledge that leaves when people do. Interviewers use "how do you document your work?" to probe seniority, and for ML roles documenting data, assumptions and model limits is part of responsible practice.

## Concept
Good documentation answers the reader's real question at the right level, and stays close to the code so it doesn't rot. A useful split (the **Diataxis** framework):
- **Tutorials**: learning-oriented, step by step.
- **How-to guides**: task-oriented recipes ("how to retrain the model").
- **Reference**: precise, complete, generated where possible (API docs, config options).
- **Explanation**: background and the "why" (architecture, trade-offs).

**In the code**
- **Docstrings** on public modules, classes and functions: what it does, parameters, return value, raised errors, units and shapes. Pick one style (Google, NumPy or reST) and enforce it. Include a short example, which can double as a **doctest**.
- **Type hints** document types in a checkable way (`def predict(x: np.ndarray) -> float`).
- **Comments** explain *why* (a non-obvious constraint, a workaround), not what the code already says. Avoid stale comments.
- Good names and small functions reduce the need for comments.

```python
def zscore(xs: list[float]) -> list[float]:
    """Standardize values to zero mean and unit variance.

    Args:
        xs: Non-empty list of numbers.

    Returns:
        List of (x - mean) / std using the population std.

    Raises:
        ValueError: If xs is empty or has zero variance.

    Example:
        >>> zscore([1.0, 3.0])
        [-1.0, 1.0]
    """
```

**At the project level**
- **README**: what it is, how to install, a quickstart, how to run tests, where to get help. A new teammate should run it in minutes.
- **Architecture docs / diagrams** and **ADRs** (architecture decision records): a short file per decision with context, decision, alternatives and consequences. They capture *why*.
- **API docs**: OpenAPI/Swagger generated by FastAPI, plus examples; **changelog** and versioning (SemVer).
- **Runbooks**: how to operate, debug and recover (alerts, rollback steps).
- **Docs as code**: Markdown in the repo, reviewed in PRs, built with MkDocs or Sphinx and checked in CI (doc coverage, link checks, doctests).

**For data and ML**
- **Data dictionary / datasheet**: columns, types, units, sources, freshness, known quality issues.
- **Model card**: intended use, training data, metrics (including per-group), limitations, ethical considerations, version and owner.
- **Experiment tracking** (MLflow, W&B) with parameters, data version and code commit so results are reproducible.

Keep docs short, current and discoverable; docs that are wrong are worse than none.

## Worked example
Inheriting a churn model with no docs costs a new hire days. Add: a README with `make setup && make train` (30 minutes to first run), a model card (trained on 2023-24 US subscribers, AUC 0.84, recall drops from 0.71 to 0.55 for users under 30 days tenure, do not use for enterprise accounts), an ADR "Use gradient boosting over a neural net: similar AUC, 10x cheaper to serve, easier to explain", and a runbook ("If PSI on `tenure` exceeds 0.2, retrain with `make train DATE=...`"). Docstring coverage in CI is checked at 90% for public functions.

> [!TIP] Interview tips
> - Say what you document and where: docstrings and types in code, README and ADRs in the repo, model cards and data dictionaries for ML.
> - Stress keeping docs close to code, reviewed in PRs and tested (doctests, link checks) so they don't rot.
> - Explain that comments say why, not what, and that a good README gets a new engineer productive in under an hour.
