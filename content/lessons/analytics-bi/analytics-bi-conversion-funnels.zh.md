## 为什么重要
漏斗展示了用户在通往购买或注册等目标的路上在哪里流失。面试官会让你定义步骤，用 SQL 计算各步骤和整体转化率，并解释如何诊断和改进最大的漏点。

## 概念
**漏斗**是一组有顺序的步骤（浏览 → 加入购物车 → 结账 → 购买）。对每个步骤统计到达它的用户（或会话）数。

- **步骤转化率** $= \dfrac{\text{第 } k \text{ 步用户数}}{\text{第 } k-1 \text{ 步用户数}}$。
- **整体转化率** $= \dfrac{\text{最后一步用户数}}{\text{第一步用户数}}$，即各步骤转化率的乘积。
- **流失率** $= 1 - \text{步骤转化率}$。*绝对*流失用户数最多的步骤，通常是最值得优化的目标。

**设计决策**（要明确说明）：
- **单位**：用户还是会话。会话漏斗衡量流程本身；用户漏斗包含稍后回来完成的情况。
- **严格顺序与宽松顺序**：步骤是否必须按顺序发生？严格漏斗要求每一步的首次时间晚于上一步。
- **转化窗口**：例如首次浏览后 7 天内购买。
- **进入队列**：只有到达第 1 步的用户才计入；没有浏览却购买的用户要排除（或标记为埋点问题）。

**SQL 模式**：先聚合为每个用户一行，记录各步骤的首次时间（`MIN(CASE WHEN event = ... THEN ts END)`），再统计满足顺序条件的用户数。不要数事件：一个用户浏览 5 次只算一个用户。

**诊断**：按设备、渠道、国家、新老用户细分；比较转化耗时；检查漏点步骤是否有技术错误；然后对修复方案做 A/B 测试。渠道结构变化时要警惕辛普森悖论。

## 示例讲解
5 名浏览用户的漏斗：3 人加入购物车，1 人按顺序完成购买。

| 步骤 | 用户数 | 步骤转化率 | 整体 |
|---|---|---|---|
| 浏览 | 5 | 不适用 | 100% |
| 加购 | 3 | $3/5 = 60\%$ | 60% |
| 购买 | 1 | $1/3 \approx 33\%$ | 20% |

整体 $= 0.6 \times 0.333 = 20\%$。*相对*漏点最大的是加购到购买（流失 67%），而两个步骤的绝对流失用户数都是 2 人。数字更大时，应按绝对流失用户数乘以修复该步骤的预期价值来排序。

查询结构：

```sql
WITH u AS (
  SELECT user_id,
         MIN(CASE WHEN event = 'view' THEN ts END) AS v,
         MIN(CASE WHEN event = 'cart' THEN ts END) AS c,
         MIN(CASE WHEN event = 'purchase' THEN ts END) AS p
  FROM events GROUP BY user_id
)
SELECT COUNT(v) AS viewers,
       COUNT(CASE WHEN c >= v THEN 1 END) AS carted,
       COUNT(CASE WHEN c >= v AND p > c THEN 1 END) AS purchased
FROM u;
```

> [!TIP] 面试技巧
> - 写 SQL 之前先说明单位（用户还是会话）、顺序（严格还是宽松）和转化窗口。
> - 同时报告步骤转化率和整体转化率，并按绝对流失用户数乘以修复价值来排序漏点，而不只看百分比。
> - 提到要验证漏斗：跳过某一步的用户通常说明埋点有缺口，而不是用户行为。
