## 为什么重要
让业务用户用自然语言提问，是最常见的 LLM 产品之一，也是最容易出现隐蔽错误的产品之一。面试官会考察你如何处理大型模式、含糊的术语、错误的连接、安全性，以及如何衡量正确性。

## 概念
**流水线**：
1. **模式链接/检索**：面对数百张表，只检索相关的表和列（对表和列的描述及示例值做嵌入），而不是把整个模式全部塞进去。
2. **提示词**：DDL、列描述、主要关系、少量示例行或取值、业务定义（“活跃用户 = 28 天内至少 1 次会话”），以及 few-shot 的问题/SQL 对，最好按相似度检索。
3. **生成**：低温度，通常明确指定 SQL 方言。
4. **执行前验证**：解析 SQL，只允许单条只读 `SELECT`，表白名单，强制 `LIMIT`，设置超时，并使用带行级安全的只读角色。
5. **执行与自我纠正**：出错或结果为空时，把信息反馈给模型，重试 1-3 次。
6. **解释**：展示 SQL 和假设，便于用户核实。

**失效模式**：幻觉出不存在的列；连接键错误或**扇出（fan-out）**（连接一对多的表会复制行，使 `SUM` 偏大）；指标和时间范围含糊；方言差异；能正常执行却悄悄给出错误答案。缓解办法：**语义层**（受管控的指标定义，由模型选择而非自创）、澄清性问题，以及展示查询语句。

**评估**：**执行准确率**（把结果集与标准 SQL 的结果比较）优于字符串精确匹配，因为很多查询是等价的。基准：Spider、BIRD（脏的真实数据）。用真实问题构建内部评测集，并在生产中监控。

**安全**：控制点是数据库角色，而不是提示词。不要依赖“只写 SELECT”的指令；提示词注入可能来自表中的数据。

## 示例讲解
一个数据仓库有 200 张表、2,500 列。把整个模式放进去约需 60,000 token；检索前 5 张表（约 40 列）约需 2,000 token，减少 97%，干扰项也更少。

扇出：`orders` 每个订单一行，`total` 为 \$50。一个订单有 3 个 `order_items`。问题“总收入”若生成为 `SELECT SUM(o.total) FROM orders o JOIN order_items i ON i.order_id = o.id`，该订单会得到 3 × \$50 = \$150，而不是 \$50。查询不会报错，这就是为什么要用已知答案测试，并优先使用语义层指标（仅对 `orders` 做 `SUM(total)`）。
