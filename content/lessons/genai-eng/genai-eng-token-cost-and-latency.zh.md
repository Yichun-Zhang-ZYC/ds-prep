---

## 为什么重要
“这个功能在每天 100 万次请求时成本是多少？你怎么让它更快？”是核心的 GenAI 系统设计问题。好的回答会从 token 出发做算术，知道输出 token 在价格和延迟上都占主导，并列出具体的优化手段。

## 概念
**成本**按 token 计，价格按每 100 万 token 报价，输入和输出费率分开（输出通常贵几倍，常见 3 到 5 倍）：

$$\text{cost} = \frac{n_{in} \cdot p_{in} + n_{out} \cdot p_{out}}{10^6}$$

隐藏的 token 来源：system prompt 和 few-shot 示例（每次调用都重发）、聊天历史、检索到的 RAG 片段、工具定义和结果，以及**推理 token**（按输出计费）。不同模型的分词器不同；一个 token 大约是 4 个英文字符或 0.75 个单词，非英文文本和代码每个词通常消耗更多 token。要用厂商的分词器计数，而不是按词数估算。

**延迟**分为两个阶段：
- **首 token 时间（TTFT）**：网络、排队和**预填充（prefill）**，后者并行处理整个提示词；随输入长度增长。
- **解码**：以每秒 token 数（token 间延迟）逐个生成 token，所以 $\text{total} \approx \text{TTFT} + n_{out}/\text{tps}$。

输出长度是端到端时间的主要驱动因素，所以要限制它并要求简洁输出。流式输出不会缩短总时间，但会让 TTFT 成为用户感知的延迟。

**优化手段**：
- 更短的提示词（精简示例、裁剪历史、少检索几个片段、压缩工具输出）。
- **Prompt caching**：缓存的输入前缀按大幅折扣计费（通常约为基础输入价格的 10%，写入时可能有溢价），并降低 TTFT；需要稳定的前缀和存活时间。
- **模型路由**：简单请求用便宜的小模型，困难请求用大模型；蒸馏或微调小模型。
- **批处理 API**：用于离线负载的异步任务，价格约为一半。
- 限制 `max_tokens`，用结构化输出代替长篇文字，并行化相互独立的调用，自托管时使用推测解码或量化。
- 对重复查询使用**语义/精确响应缓存**（见缓存课程）。

## 示例讲解
价格（示意）：输入每 100 万 token \$3，输出 \$15。一个请求有 2,000 个输入 token 和 500 个输出 token。
- 成本：输入 2000 × 3 / 10^6 = \$0.006，输出 500 × 15 / 10^6 = \$0.0075，合计 \$0.0135。
- 每天 100,000 个请求：0.0135 × 100,000 × 30 = \$40,500 每月。输出只占 20% 的 token，却占 56% 的账单。
- 以每百万 \$0.30 缓存 1,500 个输入 token：500 × 3 + 1500 × 0.3 = 1950，再加输出 7500，共 9450（单位：美元的百万分之一），即每个请求 \$0.00945，节省 30%，月账单为 \$28,350。
- TTFT 为 0.4 秒、每秒 50 个 token 时的延迟：0.4 + 500/50 = 10.4 秒。把输出减到 250 个 token 则为 5.4 秒，每个请求还可再省 \$0.00375。

> [!TIP] 面试技巧
> - 一定要计算：输入输出 token 数乘以价格再乘以调用量；指出输出 token 和推理 token 占主导。
> - 区分 TTFT（预填充，取决于输入长度）和解码（取决于输出长度）；说明流式输出只改善感知延迟。
> - 按顺序列出手段：更短的提示词、缓存、路由到更小的模型、批处理、响应缓存。
