## 为什么重要
语音智能体（电话客服、免下车点餐、语音助手）看起来像带麦克风的聊天机器人，实则是一个实时系统问题。人们对超过约 1 秒的停顿很敏感，也讨厌被打断，所以这道面试题的实质是：“如何在保证模型准确与安全的同时，满足对话级的延迟预算？” 

## 概念
两种架构：
- **级联流水线**：流式 **STT**（语音转文字）→ LLM（带工具）→ 流式 **TTS**（文字转语音）。各环节可替换，能得到文字转录用于日志、评测、PII 脱敏和护栏，工具调用与一般智能体相同。延迟是各环节之和。
- **语音到语音模型**（通过 WebSocket/WebRTC 原生音频输入输出）：延迟更低，保留语调和情绪，但文本层面的控制较弱，评测和脱敏更难，工具和声音选择更少。受监管或工具密集的流程中，很多团队仍选择级联。

**延迟预算**（语音到语音，从用户停止说话到听到第一段音频）：

$$T \approx T_{endpoint} + T_{stt} + T_{ttft} + \frac{n_{first}}{\text{tps}} + T_{tts} + T_{net}$$

目标（示意）：低于约 800 ms 感觉自然，1.5 s 就显得迟钝。优化手段：
- **全程流式**：用户说话时就运行 STT，流式输出 LLM token，在**第一句/第一个分句**就开始 TTS，而不是等完整回复（让 $n_{first}$ 很小）。
- **端点检测/轮次判断**：语音活动检测（VAD）等待一段静音窗口（如 300 到 500 ms）。太短会打断用户思考，太长会增加空白。语义轮次检测器（这句话听起来说完了吗？）允许更短的窗口。
- **打断（barge-in）**：播放期间 VAD 听到用户说话时，立即停止 TTS、清空音频缓冲、取消正在进行的 LLM 调用，历史中只记录实际*播出*的内容。
- 说话路径使用**快速模型**（小模型、提示缓存、短输出）；慢工具调用时用过渡语（“我帮您查一下”）掩盖，或把重推理放到后台。
- **区域与传输**：WebRTC/WebSocket，STT、LLM、TTS 同区部署，避免冷启动。

**常见陷阱**：为眼睛写的文本（列表、URL、markdown）听起来很糟，要让模型用简短平实的句子说话，并在 TTS 前规范化数字、日期和拼写。STT 对姓名、邮箱和数字容易出错，需要复述确认。回声和背景噪声会让智能体听到自己（使用回声消除）。电话音频只有 8 kHz，会降低准确率。对付款、取消等操作要确认，保留转人工通道，并处理录音同意和 PII。

## 示例讲解
场景：药房续药热线。实测基线（示意）：端点检测 400 ms，STT 最终结果 100 ms，LLM 首 token 延迟 300 ms、速度 50 token/s，TTS 首字节 120 ms，网络 80 ms。回复共 60 个 token。

1. **不流式**（等完整回复再合成）：$400 + 100 + (300 + 60/50 \cdot 1000) + 120 + 80 = 2200$ ms。来电者听到 2.2 秒的沉默。
2. **流式并在第一句切分**（12 个 token）：LLM 部分为 $300 + 240 = 540$ ms，总计 $400 + 100 + 540 + 120 + 80 = 1240$ ms。
3. **更快路径**：更小的模型加缓存提示（TTFT 200 ms，80 token/s）、简短的首个分句（8 个 token）、250 ms 窗口的语义轮次检测：$250 + 100 + (200 + 100) + 120 + 80 = 850$ ms。

准确性护栏仍然保留：智能体会复述药品名和出生日期（“是 Sam Rivera，3 月 3 日出生吗？”），因为这里的 STT 错误代价很高，续药在调用工具前也要确认。用录音通话评测：实体词错误率、任务完成率、被打断/截断率、p50/p95 语音到语音延迟、转人工率。

> [!TIP] 面试技巧
> - 把延迟预算写成各环节之和，并说明你会先优化哪一项（通常是：流式 + 首句 TTS，然后是端点检测）。
> - 明确提到打断、端点检测和回声；这些是区分语音体验与聊天体验的地方。
> - 把安全关键逻辑（认证、确认）放在代码中，并说明你用真实通话音频而不只是文本来评测。
