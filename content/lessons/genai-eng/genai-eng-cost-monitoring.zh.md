## 为什么重要

LLM 支出按用量计费，一次提示词改动、一个重试循环或一个重度客户就可能让支出一夜之间暴涨 10 倍。面试官想听你如何归因成本、设置预算和告警，以及如何在不损害质量的前提下降低账单。


## 概念

**先算单位经济账**：每次请求的成本 $=\dfrac{t_{in}\,p_{in} + t_{out}\,p_{out}}{10^6}$，价格按每百万 token 计。输出 token 的价格通常是输入的 3-5 倍，所以长生成占主导。再加上嵌入、重排器调用、向量数据库、工具/API 费用以及重试。然后计算每个**业务单元**的成本：每次对话、每个已解决的工单、每个活跃用户。与价值（收入、节省的人时）比较得到毛利。

**归因**：给每次调用打上功能、提示词版本、模型、租户/团队、环境和请求 id 标签。没有标签，你能看到账单却看不到原因。从供应商响应的 `usage` 字段读取 token 数（不要估算），单独记录缓存 token 数，并将你的合计与发票对账。

**控制措施**：
- 按租户和功能设置**预算与速率限制**；对 `max_tokens`、上下文长度、工具循环次数和重试设置硬上限（失控的智能体循环是典型的成本事故）。
- **告警**：绝对的每日/每小时预算，以及**异常检测**（今天对比近期均值加 $k$ 个标准差，并为标准差设置下限，使平稳的历史不会对噪声告警）；对每请求成本和每请求 token 数告警，而不仅是总支出，以区分流量增长与效率下降。
- **仪表盘**：按功能/模型/租户的成本、每请求 token 的 p95、缓存命中率、重试率、支出最高者。

**降本手段**（每次之后都在评测集上衡量质量）：把简单请求路由到更小的模型（级联或分类器路由）、缩短提示词、对稳定前缀使用提示词缓存、缓存响应、限制输出长度、离线工作使用批处理 API（有折扣、异步）、检索更少的片段，以及为高流量任务蒸馏或微调小模型。

**延迟与成本的权衡**：最便宜的方案不一定可接受；要跟踪每次*成功*结果的成本，因为重试和失败的回答同样花钱。


## 示例讲解

某客服助手每天处理 50,000 个请求，平均 1,200 个输入 token 和 300 个输出 token，价格为每百万输入 token \$2.50、每百万输出 token \$10。

每个请求：输入 1,200 × \$2.50 / 10^6 = \$0.003，输出 300 × \$10 / 10^6 = \$0.003，合计 \$0.006。每天：50,000 × \$0.006 = \$300，每月约 \$9,000。

随后一次发布增加了自我批评步骤，每个请求最多重试模型 4 次。流量不变，但每请求调用次数从 1 变成 4，所以每日成本变为约 \$1,200。总支出告警要等钱花掉之后才触发；**每请求 token 数**告警在一小时内就会触发，而 `prompt_version` 标签会指出元凶。

修复方案：把迭代次数上限设为 2，把批评步骤路由到小模型（比如每百万 \$0.25 / \$1），并加缓存。在评测集上验证质量保持不变。

> [!TIP] 面试技巧
> - 从单位经济账入手：每请求成本 = token 数乘以价格，输出 token 更贵；然后是每个业务结果的成本。
> - 说出控制措施：用于归因的标签、基于 usage 字段的核算、按租户的预算、token 和循环次数上限、对成本和每请求 token 数的异常告警。
> - 列出降本手段并附上质量提醒：模型路由、提示词与响应缓存、更短的提示词、批处理 API、蒸馏；每一项都必须在评测集上验证。
