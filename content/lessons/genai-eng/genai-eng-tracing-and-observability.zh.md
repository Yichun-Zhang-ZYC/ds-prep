## 为什么重要

LLM 应用是多步骤流水线（检索、重排、调用、工具、再次调用），其中有不确定的步骤。当答案出错或变慢时，你需要确切看到是哪一步造成的。“你如何调试线上的坏答案？”是标准问题。


## 概念

**Trace（追踪）**= 一次端到端请求；**span（跨度）**= 其中一个有计时的步骤（检索、一次 LLM 调用、一次工具调用），通过父 id 形成树。这是 OpenTelemetry 的模型；LLM 工具（LangSmith、Langfuse、Arize Phoenix、Helicone）和 OTel GenAI 语义约定都遵循它。

**每个 span 要记录什么**：
- 标识和计时：trace id、span id、父 span、名称、开始/结束时间、状态或错误。
- LLM span：模型 + 快照、提示词版本、**完整的提示词和补全**（或脱敏/抽样副本）、输入/输出 **token 数**、参数、结束原因、首 token 时间（TTFT）、成本。
- 检索 span：查询、top-k 文档 id 和分数、过滤条件。
- 工具 span：名称、参数、结果、错误。
- 请求级别：用户/会话 id（哈希）、功能开关、反馈（点赞/点踩、编辑）、评测分数。

**要绘制的指标**（由追踪聚合）：每一步的 p50/p95/p99 延迟、错误和超时率、每请求的 token 数和成本、缓存命中率、检索命中质量、拒答和护栏触发率、用户反馈率。

**自身耗时 vs 总耗时**：span 的总时长包含其子 span。**自身耗时** = 时长 $-$ 子 span 时长之和（子 span 顺序执行时），显示时间真正花在哪里。优化自身耗时最大的步骤，或者并行运行相互独立的步骤。

**LLM 特有需求**：查看输入/输出（而不仅是状态码）、并排比较不同运行、把失败的追踪变成**评测用例**，并对抽样的线上追踪运行在线评测（LLM 评审或规则）。对于流式输出，记录 TTFT 和每秒 token 数，而不仅是总时间。

**实际考虑**：抽样（例如 100% 的错误、5% 的成功）以控制存储；导出前对 PII 脱敏；跨服务和异步队列传播追踪上下文；原始提示词的保留期要短。


## 示例讲解

一次 RAG 请求耗时 1,800 ms。追踪树（毫秒）：

| span | 父 span | 开始 | 结束 | 总耗时 | 自身耗时 |
|---|---|---|---|---|---|
| request | 无 | 0 | 1800 | 1800 | 40 |
| embed_query | request | 10 | 50 | 40 | 40 |
| retrieve | request | 50 | 170 | 120 | 30 |
| vector_search | retrieve | 60 | 150 | 90 | 90 |
| rerank | request | 170 | 370 | 200 | 200 |
| llm_call | request | 370 | 1770 | 1400 | 1400 |

核对：根 span 的子 span 之和为 $40+120+200+1400 = 1760$，所以根的自身耗时 $= 1800 - 1760 = 40$ ms（胶水代码）。`llm_call` 占延迟的 78%（$1400/1800$）。优化手段是更小的模型、更短的提示词或输出、流式输出（TTFT 让它*感觉*更快）以及缓存，而不是更快的向量数据库（90 ms）。

> [!TIP] 面试技巧
> - 定义 trace 与 span，并说出你在 LLM span 上记录什么：提示词版本、完整输入输出、token、TTFT、成本。
> - 用自身耗时找出瓶颈；在 LLM 流水线中通常是生成步骤，所以要谈输出长度、模型大小、流式输出和缓存。
> - 形成闭环：失败的线上追踪变成评测用例，抽样的追踪做在线评测；提到抽样和 PII 脱敏。
