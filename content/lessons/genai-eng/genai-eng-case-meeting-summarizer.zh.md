## 为什么重要
摘要看起来是最简单的 LLM 任务，实际上很难上线：输入超出你愿意放进单个提示词的长度，说话人与 ASR 错误让转写文本混乱，而流畅的摘要可能悄悄编造一个决定或负责人。面试官想看到策略选择（长上下文 vs map-reduce）、结构化输出和真实的评估方案。

## 概念
**澄清**：读者是谁（与会者、缺席者、高管）、格式（要点、决定、带负责人和截止日期的待办事项）、长度、语言、隐私（录音、同意、保留期）、延迟（实时纪要 vs 会后）。

**会议流水线**：音频 → 带说话人分离的 ASR（说话人标签、时间戳）→ 清理（去除口头语，用术语表或会议邀请中的参会者名单修正人名和行话）→ 分段（按话题转换、时间窗口或发言轮次，绝不在句中切断）→ 摘要 → 抽取结构化条目 → 核验 → 交付。

**长度策略**：
- **长上下文一次处理**：转写文本能轻松放下时（比如 < 5-10 万 token）最简单、最连贯。注意“中间丢失”：要求附带带时间戳的证据引用。
- **Map-reduce**：对每个块做摘要（并行），再对局部摘要做归约；若摘要超过窗口则增加层级（分层）。易于并行并可扩展到任意长度，但会丢失跨块上下文：传入简短的滚动“上下文”或议程，并让块之间略有重叠。
- **Refine**（迭代）：让一个滚动摘要贯穿各个块。串行、较慢，但保留叙事流畅性；错误会累积。
- 当用户问具体问题而非要总览时，使用面向查询的摘要（对转写文本做 RAG）。

**结构优于散文**：输出模式（`decisions[]`、`action_items[] {owner, task, due, source_timestamp}`、`open_questions[]`、`summary`），未知负责人填 null；不要让模型指派没有说过的负责人或日期。

**评估**：ROUGE 等重叠度指标与实用性的相关性很弱。更好的做法：(1) **忠实度**：把摘要拆成论断，逐条对照转写文本检查（NLI 或 LLM 评判，见 LLM-as-a-judge 课程）；(2) **覆盖率**：人工标注的要点有多少出现在摘要里；(3) 对照标注条目的**待办事项 F1**；(4) 抽样做人工偏好评估；(5) 长度和冗余。编造决定和负责人属于一级严重错误，要单独汇报。

**常见坑**：ASR 对人名和数字的错误被放大为自信的错误论断、说话人归属错误（明明是 Bob 说的却写成“Alice 说”）、偏重会议末尾的近因偏差、块边界切断了一次讨论、摘要只是复述议程而非发生了什么、没有同意/保留期政策。

## 示例讲解
示意：一场 90 分钟的会议，约每分钟 150 词，共 13,500 词，大约 18,000 token。价格为每百万 token \$3 / \$15。

- **一次处理**：18k 输入 + 1k 输出 $= 0.054 + 0.015 = 0.069$ 美元，只需一次调用，连贯性最好。
- **Map-reduce**，块大小 4,000 token、重叠 400：步长 3,600，因此块数 $\lceil (18000-4000)/3600 \rceil + 1 = 4 + 1 = 5$。Map：约 21k 输入（各块加每次 200 token 的指令）和 5 x 300 = 1.5k 输出；reduce：1.7k 输入、800 输出。成本 $= 0.063 + 0.0225 + 0.0051 + 0.012 \approx 0.103$ 美元；若 reduce 每次归并 4 个，则共 8 次调用（5 次 map + 2 + 1），但 map 可以并行。
- 因此 90 分钟的会议用一次处理；10 小时的工作坊（约 20 万 token）则用分层 map-reduce，并把议程传给每次 map 调用。
- 质量门槛：抽取了 12 个待办事项，人工参考有 10 个；其中 9 个匹配，3 个无依据（编造了负责人或日期）。精确率 $= 9/12 = 0.75$，召回率 $= 9/10 = 0.9$。这 3 个无依据条目促使我们采用更严格的规则：“只有明确说过才填负责人和截止日期，并附带时间戳引用”。

> [!TIP] 面试技巧
> - 先问读者是谁、需要什么格式；提出结构化输出（决定、带负责人和时间戳的待办事项）而非自由散文。
> - 从成本、连贯性和并行性比较长上下文一次处理、map-reduce 与 refine 的取舍。
> - 按论断评估忠实度，评估要点覆盖率和待办事项 F1；只看 ROUGE 不够。
