## 为什么重要
代码助手是最具代表性的 LLM 产品，面试官借它考察上下文工程（从百万行代码库里该把什么放进提示词？）、带真实工具的智能体循环，以及有测试提供可验证信号的评估。同一套骨架覆盖行内补全、聊天、自动 PR 审查和自主修 bug 的智能体。

## 概念
要把三类产品区分开；它们的延迟、上下文和风险各不相同。

- **行内补全**：延迟预算只有几百毫秒。使用小而快的模型、fill-in-the-middle（前缀 + 后缀）提示，上下文来自当前文件、相邻标签页和最近的编辑，并在用户输入时做激进的缓存和取消。指标：采纳率、每用户采纳字符数、延迟 p50/p95。
- **代码库聊天/问答**：对代码而非散文做检索。按 AST 单元（函数、类）分块，带文件路径和签名，把嵌入检索与精确搜索（grep、符号索引、调用图）结合，再重排。要包含编辑中引用到的符号的定义，而不仅是相似文本。
- **自动 PR 审查**：输入是 diff 加上下文（完整的被改文件、调用方/被调用方、测试、风格指南、PR 描述）。输出必须是*少而具体、可执行*的评论，带文件/行锚点和严重程度。先运行静态分析和测试，让模型解释或分诊其结果；模型最擅长发现逻辑疏漏、缺失的边界情况和命名不清。按置信度过滤，与已有评论去重，并从“已解决/已驳回”的反馈中学习。
- **智能体编程**：在沙箱里循环执行 读文件 → 修改 → 运行测试/linter → 读错误 → 修复，并限制预算（步数、token、时钟时间）。工具：搜索、读取、打补丁、shell、测试运行器。测试是奖励信号；要求先有一个失败的测试，修复后通过。合并前保留人工审批。

**安全**：把仓库内容、issue 和网页都当作不可信（提示注入可能索取密钥或外泄数据）；在无网络、无密钥的沙箱中执行；扫描生成代码中的密钥、易受攻击的模式和许可证问题；绝不让智能体直接推送到受保护分支。

**评估**：可执行的基准（单元测试；SWE-bench 风格的 issue 解决；生成任务的 $pass@k$），再加上你自己的真实工单回归集。对审查，标注一批评论（有用/噪声/错误），跟踪精确率和*已解决率*；对补全，跟踪采纳率和编辑后保留率。LLM 打分的质量需要人工校准。

**常见坑**：幻觉出不存在的函数或库版本（要以仓库的依赖文件和文档为依据）、索引过期、上下文塞满无关文件、嘈杂的审查评论让开发者学会忽略机器人、智能体通过改测试来作弊、只在模型可能见过的公开基准上评估。

## 示例讲解
示意：审查机器人上线。每周 1,000 个 PR。原始模型每个 PR 给出 5 条评论，共 5,000 条；人工标注样本显示 35% 有用，也就是 1,750 条有用评论混在 3,250 条噪声里，开发者开始屏蔽这个机器人。

加入流水线：静态分析作为依据、第二遍“这真的是 bug 吗？”的验证器、置信度截断、去重，并限制每个 PR 最多 3 条评论，按严重程度排序。结果：每个 PR 1.5 条评论 = 1,500 条，70% 有用 = 1,050 条有用评论。
- 精确率从 35% 翻倍到 70%；保留的有用评论 $= 1050/1750 = 60\%$。
- 这是正确的取舍：机器人靠信任来评判。用已解决率（评论之后出现了代码修改）作为线上指标，并据此调节截断阈值。
- 成本：每个 PR 约 16k 输入 token（6k diff + 10k 上下文）和 1k 输出，共 3 次调用（审查、验证、总结）：每个 PR 约 50k token，对共享的仓库上下文做提示词缓存可大幅降低输入费用。

智能体版本：修 bug 的智能体对每个 issue 采样 10 次，其中 3 次通过测试，则 $pass@1 = 0.3$，而 $pass@5 = 1 - \binom{7}{5}/\binom{10}{5} = 1 - 21/252 \approx 0.917$。把采样与验证器或“以测试作为选择器”结合，才能把 pass@k 变成真实的成功率。

> [!TIP] 面试技巧
> - 把产品拆成补全、聊天、审查和智能体四类；它们的延迟、上下文和风险各不相同。
> - 讲上下文工程：AST 分块、符号与调用图检索、混合检索、缓存。
> - 使用可验证信号（测试、pass@k、已解决率），为智能体设沙箱，把仓库文本当作不可信输入。
