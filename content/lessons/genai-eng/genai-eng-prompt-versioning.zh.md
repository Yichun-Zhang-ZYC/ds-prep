---

## 为什么重要

提示词是没有编译器的代码，改一个词就可能悄悄破坏下游解析器。面试官会问你如何安全地发布提示词变更：版本管理、评测门禁、发布和回滚。


## 概念

**把提示词当作有版本的制品**，而不是埋在应用代码里的字符串。

**需要一起版本化的内容**：模板文本、模型名称和快照、采样参数（temperature、max tokens）、输出 schema、工具定义、少样本示例以及检索设置。“提示词版本”实际上是一个**配置包**；仅更换模型对行为的影响可能不亚于修改文本。

**存储方案**：与代码一起放在 git 中（可评审，与发布绑定），或放在提示词注册表/CMS（LangSmith、Langfuse、PromptLayer、数据库）中，这样非工程师也能编辑，并且无需重新部署即可更改提示词。无论哪种方式，都要保留**不可变的版本**（1、2、3 或内容哈希），再加上指向某个版本的**可变别名**（`prod`、`staging`）。回滚就是移动别名。

**发布流程**：
1. 在分支上编辑；记录变更原因。
2. 对照基线运行**离线评测**（黄金集 + 回归用例 + schema 有效性和安全检查）。在相同输入上做配对比较。
3. **影子或金丝雀**：在一小部分线上流量（1-5%）上运行候选版本，比较线上指标（点踩率、升级人工率、成本、延迟）。
4. 提升别名；保留旧版本以便即时回滚。

**可追溯性**：在每个请求的日志/追踪上打上 `prompt_name`、`prompt_version` 和模型，使回归可以追溯到某次变更。保存输入和输出以便重放。

**陷阱**：评测集太小，无法检测差异；修复一个案例却让其他案例退化的提示词修改；悄悄变化的模板变量（缺失字段渲染为空文本）；以及供应商更新模型别名导致的漂移。请固定带日期的模型快照。


## 示例讲解

`support-reply` 的 v3 在生产环境中，在 200 个黄金案例中通过 184 个（92%）。候选版本 v4 通过 178 个（89%），但因为更短而便宜 30%。

v4 更差吗？每个通过率的标准误约为 $\sqrt{0.9 \cdot 0.1 / 200} \approx 0.021$，所以 3 个百分点的差异的标准误 $\approx 0.021\sqrt2 \approx 0.03$。这大约是 1 个标准误：在噪声范围内。不要仅凭这个决定。对 6 个案例的净差异做**配对**检查（哪些案例翻转了，是不是关键案例？），扩充评测集，然后以 5% 做金丝雀，观察升级人工率和每工单成本。

如果金丝雀出现回归，`set_alias("support-reply", "prod", 3)` 几秒钟就能回滚，因为 v3 从未被删除。

> [!TIP] 面试技巧
> - 把提示词版本描述为一个配置包（文本 + 模型 + 参数 + schema + 示例），包含不可变版本和可变别名。
> - 讲清发布路径：在黄金集上做离线评测、线上流量金丝雀、提升、即时回滚；给每条追踪打上提示词版本标签。
> - 陷阱：在小评测集上凭几个百分点的差异就宣布胜者；提到配对比较和置信区间。
