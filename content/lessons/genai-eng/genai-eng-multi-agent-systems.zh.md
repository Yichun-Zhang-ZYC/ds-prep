## 为什么重要
“我们应该使用多个 agent 吗？”是一道经典的设计题。诚实的回答通常是“一开始不要”：多智能体系统消耗更多 token 且更难调试，但当工作可以并行，或需要隔离的上下文和专用工具时，它就有优势。

## 概念
**常见拓扑**：
- **编排者-工作者（supervisor）**：主 agent 做计划，把子任务（通常并行）委派给工作者，并综合结果。深度研究类系统使用这种方式。
- **移交/路由**：分诊 agent 把对话交给某个专家（计费、技术支持），之后由专家负责。
- **流水线/顺序**：规划者，然后编码者，然后审查者；每个 agent 的输出是下一个的输入。
- **辩论/评论者**：agent 提出方案并相互批评；由裁判或投票决定。在某些任务上能提升推理或事实性，但成本很高。
- **对等/集群**，使用共享状态或黑板：灵活，但最难控制。

**为什么拆分**：(1) **上下文隔离**：每个工作者拿到只含所需信息的全新窗口，避免单个上下文过载；(2) **并行**：广度优先的任务（研究、大量文件）完成得更快；(3) **专业化**：每个角色有各自的 prompt、工具和模型（抽取用便宜模型，规划用强模型）；(4) **权限**：每个 agent 使用最小权限的工具。

**为什么不拆**：多智能体运行消耗的 token 往往是单 agent 的数倍（公开报告称研究型系统比聊天高约一个数量级）、协调错误（重复工作、冲突的编辑、agent 之间做摘要时丢失信息）、非确定性以及难以调试。紧密耦合或需要共享状态的任务（单个模块内的大部分编码）更适合单 agent。

**工程要点**：结构化、精简的移交消息（摘要加引用，而不是原始记录）；为每个工作者给出明确的任务描述，含范围、输出格式和停止条件；步数/token 预算和超时；为失败的工作者设置重试和回退；共享记忆或产物存储；按 agent 做追踪（见“追踪与可观测性”）；对整个系统和每个角色分别评估。框架：LangGraph、AutoGen、CrewAI、OpenAI Agents SDK、Claude Agent SDK，以及用于跨厂商 agent 通信的 A2A 协议。

**默认建议**：从一个 agent 加好用的工具开始；只有当你能说出第二个 agent 要消除的瓶颈（上下文、并行、专业化、权限）时才加入它。

## 示例讲解
任务：比较 4 个竞争对手。单 agent：一个上下文总共 3 万 token。

编排者-工作者：规划者 3k token，4 个工作者（并行）各 25k = 100k，综合 8k。总计 = $3 + 100 + 8 = 111$k token，是 $111/30 = 3.7\times$ 的 token。墙钟时间：大约是最慢的工作者加上规划和综合，而不是四次顺序研究之和，所以延迟降到约三分之一（示意）。如果每个工作者独立成功的概率为 90%，四个都成功的概率是 $0.9^4 = 0.656$，所以编排者需要重试和部分结果处理，而不能假设所有工作者都会成功。

> [!TIP] 面试技巧
> - 以“先用单 agent”开头，并用具体瓶颈来论证多 agent：并行、上下文隔离、专业化或权限。
> - 量化成本：更多 token、更大的延迟方差（长尾工作者）、跨工作者累积的失败概率。
> - 讨论移交契约、预算、按 agent 追踪，以及如何端到端评估系统。
