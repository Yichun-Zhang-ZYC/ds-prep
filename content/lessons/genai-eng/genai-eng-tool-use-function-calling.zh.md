---

## 为什么重要
工具调用把 LLM 从文本生成器变成能查询数据库、调用 API 并执行动作的系统。面试官想看到你理解：到底由谁来执行工具、如何校验模型生成的参数，以及如何处理错误。

## 概念
**循环**：你把对话和**工具定义**（名称、描述、参数的 JSON Schema）发给模型。如果模型认为需要工具，它返回结构化的**工具调用**（`name`、`arguments`、调用 id），而不是最终文本。**由你的代码执行它**（模型从不运行任何东西），再追加一条以调用 id 为键的**工具结果**消息，然后再次调用模型。重复直到模型返回纯文本。OpenAI 称之为函数调用（`tools`、`tool_calls`）；Anthropic 使用 `tool_use` / `tool_result` 内容块；开源模型使用聊天模板约定，vLLM 等服务器提供兼容 OpenAI 的接口。

**好的工具设计**：
- 清晰的名称和描述（描述就是“何时使用它”的 prompt）、职责单一、带类型的参数并给出枚举和示例；工具要少（列表变长后准确率会下降，所以要对工具定义做路由或检索）。
- 返回紧凑、模型易读的结果（裁剪过大的负载；包含单位和 ID），并且**把错误作为结果返回**（`{"error": "city not found"}`），这样模型可以重试或询问用户。
- **永远不要信任参数**：对照 schema 校验，在服务端强制授权，SQL 使用参数化，对破坏性或高成本的操作（支付、删除）要求人工确认。

**控制手段**：`tool_choice`（auto、required、指定某个工具、none）；调用相互独立时使用**并行工具调用**；**strict / 结构化输出**使参数符合 schema，但语义有效性（真实存在的订单 id）仍需检查。设置最大迭代次数、超时，并为有副作用的工具使用幂等键。

**失败模式**：选错工具、幻觉参数、缺少必填参数（应该询问用户）、无限循环，以及通过工具结果传入的 prompt 注入（把结果当作不可信数据）。

## 示例讲解
用户：“巴黎和罗马的天气怎么样，用华氏度？”工具：`get_weather(city: string, unit: "c"|"f")`。

1. 模型在一轮中返回两个独立调用：`get_weather(Paris, f)`，id 为 `c1`；`get_weather(Rome, f)`，id 为 `c2`。
2. 应用并发执行两者，返回结果 `{id: c1, 64}` 和 `{id: c2, 72}`。
3. 模型回复：“巴黎 64F，罗马 72F。”

总计：2 次模型调用（而不是 3 次），因为调用是并行的。如果用户说的是“我所在城市的天气”，模型应该询问是哪个城市，而不是捏造参数；校验器返回 `{"error": "missing argument: city"}` 同样会促使它修正。

> [!TIP] 面试技巧
> - 明确指出：模型提出调用，由你的应用执行。校验、权限和沙箱都在这里。
> - 提到并行调用、`tool_choice`、最大迭代次数、超时，以及把错误作为工具结果返回以便自我纠正。
> - 安全：工具结果和参数都是不可信输入（prompt 注入、SQL 注入）。最小权限，不可逆操作需人工批准。
